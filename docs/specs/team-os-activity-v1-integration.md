## Предварительные условия подключения

1. APP-01 утверждает связь TeamOS company → Core integration/installation. `company.amoAccountId` — подсказка для сопоставления, а не доказательство прав. При нескольких installations выбор должен быть явным; не брать первую найденную.
2. Вход и административные права пользователя проверяются сервером. Предпочтительный вариант — запрос через существующий backend TeamOS с его сессией и ограниченным доверенным обращением к management API Activity. Если выбран прямой браузерный доступ, доработка доверия, audience, CORS и отзыва должна быть отдельно описана в ADR; не копировать авторизационные заголовки между сервисами автоматически.
3. APP-02 предоставляет версионированный OpenAPI, доступную конфигурацию origin, справочник разрешённых сотрудников и тестовый контекст компании. Секреты межсервисного доступа остаются на сервере.
4. Прототип APP-03 открывает viewer-ссылку независимо от TeamOS и виджета. Для просмотра не требуется операторская сессия, файл токена или открытая вкладка amoCRM.

При отсутствии подключения показывать «Новый контроль активности не подключён» и конкретную причину из контракта. Не подставлять тестовый account ID и не переключаться молча на старый API.

## Экраны и действия

### Список панелей

- Название, число выбранных сотрудников, рабочее окно/часовой пояс, состояние панели.
- Действия: создать, изменить, открыть, скопировать ссылку, отключить/включить, перевыпустить ссылку.
- Пустой список, загрузка, ошибка и недоступность backend показываются раздельно.
- Отключение или перевыпуск ссылки не удаляет историю CRM Events и не меняет другие панели.

### Создание и редактирование

Минимальные поля: название, непустой список сотрудников, рабочее окно отображения и поддерживаемые настройки представления. Часовой пояс берётся из подтверждённых настроек аккаунта. Сервер валидирует принадлежность каждого сотрудника installation и все пределы значений.

ID новой панели выдаёт сервер. Для редактирования передаётся полученная revision; конфликт не затирает новый результат другого администратора. Сохранить локальный черновик и предложить загрузить актуальную версию. Не использовать прежний `setSettings({panels,tasks})` для изменения одной новой панели.

| Старое поле/возможность | Первая версия нового редактора |
| --- | --- |
| `panel_name`, `employees` | Название и состав панели |
| `work_time_from`, `work_time_to` | Окно отображения; не доказательство фактически отработанного времени |
| `pipelines` | Только при реализованной серверной семантике; иначе поле недоступно с объяснением |
| `id`, `activePanelLink` | Серверный ID и ссылка из ответа; не `Date.now()` и не самостоятельная сборка секрета |
| `operators`, планы, нормативы, «эффективность» | Отложено до согласованного контракта показателей |
| `correspondence_seconds`, `tasks_seconds`, цветовые блоки звонков | Не превращать нормативные длительности в измеренные факты; добавлять только по mapping APP-01 |
| Telegram token/chat/notifications | Не переносить в первый прототип и viewer DTO |
| Глобальный `tasks`, Imbox и срезы сделок | Остаются возможностями старого продукта до отдельного scope |

### Ссылка просмотра

Сервер выдаёт ссылку на конкретную панель со случайным ключом доступа. Пользователь может открыть её на отдельном мониторе. Это право чтения только выбранной панели, не вход в управление компанией.

При перевыпуске объяснить, что прежняя ссылка перестанет работать. Ключи не записывать в аналитику, логи, fixture и отчёты. Механизм выдачи/повторного получения ссылки и защита её хранения фиксируются APP-01/02; не хранить их в общем списке технической диагностики.

## Предлагаемый management API

Пути описывают целевые операции, а не уже доступные маршруты. Публичный proxy TeamOS и внутренний management API могут иметь разные префиксы; итоговые пути зафиксировать в OpenAPI APP-02. Контекст компании устанавливает доверенный сервер.

| Метод и условный путь | Назначение |
| --- | --- |
| `GET /api/v1/activity/panels` | Список панелей разрешённой компании |
| `POST /api/v1/activity/panels` | Создать панель; Idempotency-Key сохраняется при повторе неизвестного результата |
| `GET /api/v1/activity/panels/{panelId}` | Получить настройки и revision одной панели |
| `PATCH /api/v1/activity/panels/{panelId}` | Изменить с проверкой revision, включая enabled |
| `POST /api/v1/activity/panels/{panelId}/share-link` | Выпустить/перевыпустить ссылку с явной операцией и идемпотентным повтором |
| `GET /api/v1/activity/employees` | Разрешённые сотрудники с группами и ограниченной пагинацией |

Минимальная административная модель: `id`, `name`, `employee_ids`, `display_window`, `timezone`, `enabled`, `revision`, `updated_at`. Точные типы, optional-поля, ограничения, способ выдачи ссылки и синхронный/асинхронный результат должен задать APP-02. Для HTTP 202 показывать принятую операцию и её состояние, а не немедленный успех; если выбран синхронный CRUD, не вводить фиктивную очередь на стороне UI.

Viewer API — отдельный контракт: настройки отображения конкретной панели, сводка/таймлайн, сотрудник и событие. Приложение не должно получать список всех панелей аккаунта и фильтровать его в браузере. Подробности и курсоры ограничены серверным составом панели.

## Ошибки, кеш и совместимость

- Query keys разделены по новому модулю, подтверждённой компании/установке и панели. Ответ другой компании или старого запроса не перезаписывает текущий экран.
- `401` обрабатывается существующим механизмом входа TeamOS; `403` — нет административного доступа; `404` — панель не существует/недоступна; `409` — конфликт revision или idempotency. Точные коды ошибок уточнить в OpenAPI.
- Для `429` учитывать Retry-After. Недоступность backend показывать ошибкой, не пустым успешным списком. При неопределённом исходе создания/перевыпуска повторять исходный ключ и payload.
- Неизвестное поле/неподдерживаемый фильтр не игнорируется молча. Схема старого API и нового не объединяется одним нормализатором с fallback.
- UI-права в меню дополняют серверные проверки, но не заменяют их. Для первого управления использовать существующие административные роли TeamOS после сверки с backend, без создания отдельного логина только ради Activity.
