# Activity: матрица данных и решения первой версии

Дата сверки: 2026-09-08. Результат BASE-02 и BASE-03 [плана развития](../plans/2026-09-08-activity-backend-development.md). Это спецификация дальнейшего расширения, а не сообщение о готовности этапов 2–5. Новые внешние методы и поля ниже ещё не реализованы, если явно не указано обратное.

Пользовательский JSON задаёт нужную глубину подробностей. Скриншоты получены на другом аккаунте; сравнивать их количества и переносить персональные данные в fixture нельзя. Схему `users → slots` воспроизводить не требуется. В предоставленном примере `slots: []` означает отсутствие событий пользователя за выбранный период.

### Общий конверт события

| Поле | Источник и владелец | Текущий путь / пробел | Отсутствие и правило представления | Проверка |
| --- | --- | --- | --- | --- |
| `id` | Events, CRM Events | P1–P3 есть; уникальность `(installation_id, event_id)` | ID обязателен. В старом примере это `id_event`, а числовой `id` — не замена. | Повтор ID обновляет payload без роста количества; изоляция installation. |
| `created_at` | Events, CRM Events | P1–P3, Unix seconds / `int64` | Не подменять временем загрузки; дата UI вычисляется в timezone аккаунта. | Границы периода и одинаковые секунды у разных ID. |
| `created_by` | Events, CRM Events; имя — D | P1–P3; join с именем — представление Activity | Неизвестный ID: «Пользователь #ID»; `0`: «Автор не указан», без догадки о человеке/роботе. | Автор вне справочника не уничтожается; см. отдельный пробел ниже. |
| `type` | Events, CRM Events | P1–P3, строка без закрытого enum | Незнакомый тип хранится; нейтральное название + исходный код. | Неизвестный тип не отбрасывается и входит в общий счётчик. |
| `entity_id`, `entity_type` | Events, CRM Events | P1–P3 есть | При отсутствии метаданных показывать тип/ID; для неизвестного типа не строить выдуманный URL. | Связанный объект не смешивается с автором/задачей/примечанием. |
| `value_before`, `value_after` | Events, CRM Events | P1–P3 как RawMessage → JSONB → RawMessage | `[]`, `null`, пустая строка внутри поля имеют разный смысл. Отсутствующий payload сейчас нормализуется в `[]`. | Семантическое сравнение вложенного JSON, включая неизвестные ключи. |
| `account_id`, `_links`, `_embedded`, новые top-level ключи | Events / scope Core | В типе CRMEvent отсутствуют и при decode отбрасываются. | `linked_talk_contact_id` | Events, CRM Events | P1–P3: typed int64, owner column 000003; ноль не выводится | Без поля не угадывать контакт беседы из `entity_id` сделки. | EVT-02 реализовал совместимое поле; raw-хранилище не требуется. |
| Имя сущности | Events `with`, при необходимости отдельный справочник; Gateway | `with` сейчас не запрашивается, `_embedded` не моделируется | «Сделка #ID» / «Контакт #ID», если имени нет | Сначала оценить расширение существующего ListEvents; отдельные entity reads только при нехватке. |

Наличие вложенных подробностей в пользовательском JSON не доказывает, что все они приходят прямо из Events: это может быть уже обогащённый результат другого приложения. В событиях часто есть только `note.id`; `message.id` тоже не гарантирует текст. Эти ограничения и отдельный `linked_talk_contact_id` проверены в [официальной документации Events/Notes](https://www.amocrm.ru/developers/content/crm_platform/events-and-notes).

### Подтверждённые ограничения текущего пути

- `canonicalEvent` использует `UseNumber`; неизвестные вложенные ключи и точные числовые значения серверной JSON-канонизации не требуется заменять собственным сериализатором. JSONB может менять запись числа и порядок ключей — побайтовая идентичность не обещается. Клиенты не должны необдуманно преобразовывать большие ID в JavaScript Number.
- Невозможно восстановить разницу между отсутствующим payload и исходным `[]` после текущей канонизации. Явный `null` остаётся `null`. На EVT-02 решить, нужна ли метка исходного отсутствия; это не повод автоматически внедрять raw-object storage.
- Максимум одного `value_before` или `value_after` на входе — 32 KiB; ограничение [ответа сервиса](../../internal/serviceapi/response.go) — 3 MiB. За пределами лимита есть явный отказ, а не обрезание. Большие тексты/страницы требуют проверки EVT-02.
- `Activity.Panel` без выбранных пользователей формирует фильтр по текущему directory. Авторы вне справочника сохраняются в CRM Events, но могут не попасть в стандартную панель. ENR-03/ACT-03 должны определить видимый fallback, включая автора `0`; это не проблема повторного сбора.
- Пустая страница пагинации и отсутствие событий сотрудника за весь период — разные состояния. Сводка берётся за весь запрос, не вычисляется по полученной странице. Все сотрудники выбранного набора остаются видимыми; пропущенный summary трактуется как ноль наблюдений вместе с отдельным coverage.

## 3. Источники и минимальные внешние расширения

Сверено с официальными страницами 2026-09-08. Методы ниже — кандидаты для ENR-01 после проверки нужного поля, не универсальный HTTP-прокси и не инструкция немедленно реализовать все методы.

| Потребность | Проверенный источник | Решение для проекта |
| --- | --- | --- |
| Имена сущностей, событие по ID, заметки и их params | [Events / Notes](https://www.amocrm.ru/developers/content/crm_platform/events-and-notes): `GET /api/v4/events` с `with`, `/events/{id}`, `/{entity_type}/notes` с ID-фильтром, `/{entity_type}/notes/{id}` | Сначала расширять текущий events read; адресное чтение нужно при реальной потребности. Notes — ограниченный batch по типу родителя, а не запрос на каждую строку UI. |
| Текст/родитель/срок/текущий результат задачи | [Tasks](https://www.amocrm.ru/developers/content/crm_platform/tasks-api): `GET /api/v4/tasks/{id}` | Новый read нужен для task references; сохранять происхождение текущего состояния. `entity_type` задачи использует множественное имя ресурса, событие — свой тип: mapping задаётся allowlist. |
| Названия воронок и этапов | [Pipelines](https://www.amocrm.ru/developers/content/crm_platform/leads_pipelines): `GET /api/v4/leads/pipelines` | Кешировать ограниченный справочник; повторно не создавать GetLeadState. |
| Название/тип/enum пользовательского поля | [Custom fields](https://www.amocrm.ru/developers/content/crm_platform/custom-fields): `GET /api/v4/{entity_type}/custom_fields`, адресное чтение поля | Документация неоднозначна о размере страницы (50 в описании, 250 в limit). Безопасный старт — 50 и следование собственной пагинации до конца; проверить живым тестером. |
| Пользователи, отделы, календарные настройки | [Users](https://www.amocrm.ru/developers/content/crm_platform/users-api), [Account](https://www.amocrm.ru/developers/content/crm_platform/account-info) | Использовать существующие GetDirectory/GetUserAuthorization; не добавлять второй directory/cache. Avatar/email — отдельная необязательная задача. |

Проверенные источники не гарантируют универсальный read текста чатов или скачивание файлов в рамках OAuth CRM. Для этих данных первая версия сохраняет доступный ID/metadata; дальнейшая возможность выясняется отдельно. Доступные данные CRM зависят от прав источника, поэтому даже admin-only вход продукта не создаёт отсутствующих прав у интеграции.

Для E обязательны `source`, время получения, ID исходного объекта и состояния `pending`, `ready`, `unavailable`, `retry/error` с ограниченным reason code. Это целевые требования ENR-02, а не уже существующие поля protobuf. Не перезаписывать ими `value_before/value_after` и не создавать вторую историю в Activity.

## 4. Решения BASE-03 для первой версии

Это рабочие решения в разрешённом scope плана. Они сохраняют текущие ограничения; новые UI/API фильтры выполняются на этапах 4–5.

| Вопрос | Принятое решение | Уже есть / дальнейшая задача |
| --- | --- | --- |
| Доступ | Только активный администратор. Права руководителей отделов — отдельный серверный policy scope. | [corepolicy](../../internal/corepolicy/policy.go) уже проверяет active/admin; не дублировать проверку в renderer или обходить её фильтром отдела. |
| Период | Обязателен; точные Unix seconds. Календарный день/ввод/вывод — в timezone аккаунта. День выбирается по его календарным границам, не фиксированным 24 часам при DST. | Сейчас Query допускает ≤31×86400 секунд и `[from,to]` включительно. Для полного дня брать до следующей полуночи минус 1 секунду; новый half-open контракт не вводить молча. |
| Неизвестная timezone | Не подменять незаметно timezone браузера. Показывать явное состояние настройки/источника; числовые timestamps сохраняются. | D/timezone уже есть; UI-01 должен привести ввод периода к этой timezone. |

## 5. Синтетический набор и приёмка сохранности

[activity-events-v1.json](../fixtures/activity-events-v1.json) — проектный синтетический набор. Его оболочка (`cases`, `enrichment_samples`, `reference_users`) не является amoCRM response или новым публичным Activity API. `input` содержит события для проверки существующего типизированного пути. Некоторые вложенные расширения намеренно искусственные; `shape_kind` отличает reference-only формы от enriched/synthetic вариантов. Числа, имена и UUID вымышлены; внешние ссылки используют `.invalid`; нет записей/телефонов реальных клиентов.

Для каждого case есть `category`, `expectation`, `followup`. `current_payload_after_canonicalization` при наличии задаёт ожидаемый результат существующей нормализации. `upstream_extra_fields` перечисляет поле верхнего уровня, которое текущая модель отбрасывает; тест не должен ошибочно ожидать его сохранности уже сейчас. `enrichment_samples` — отдельные будущие ответы, их нельзя вливать в raw event как доказанное историческое значение. `reference_users[].slots` содержит только ID примеров, это иллюстрация группировки, не продуктовый контракт.
