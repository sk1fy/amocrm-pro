# Activity problem snapshots: request-driven collection

The Gateway owns one durable source per installation. Panels only select employee/pipeline counts from its last complete generation; concurrent tabs never create separate scans.

A viewer request schedules a generation only when no complete snapshot exists or the last publication is at least seven minutes old. Fresh/collecting requests do not update the row. The collector claims only non-idle generations: publication leaves it idle, so an expired deadline alone cannot launch a scan. A scheduled generation finishes even if all viewers close, including across process restart, batch pauses and retries. A new seven-minute minimum starts at publication.

Leads and unfinished tasks are fetched in fixed pages of up to 250, with the existing account-wide outgoing request budget. The durable `batch_records` counter adds actual rows from both phases. Before a possible next 250-row page could exceed `ACTIVITY_PROBLEM_BATCH_SIZE` (default 5000, allowed250..50000), the next checkpoint is delayed by `ACTIVITY_PROBLEM_BATCH_PAUSE` (default60s, allowed1s..1h). This page-boundary policy can end a batch slightly below5000 at a phase boundary, but never exceeds it. Phase/page/batch/next-poll and lease are kept in PostgreSQL; a pause does not block other accounts or require a worker to sleep. Viewer requests never shorten a pause. The final page publishes immediately without an unnecessary final pause.

Transient failure preserves checkpoint and old publication. Retry delay is at least 30s and at least upstream Retry-After; concurrent requests cannot bypass it. A lost lease cannot write a page or change retry scheduling. Permanent errors (permission denied, not found, unauthenticated, reauthorization required, invalid argument, or an upstream APIError classified as permanent) stop the generation in idle with an error and a seven-minute cooldown. They never publish staging rows or self-retry after viewers close. A later viewer request after the cooldown may start a fresh generation, allowing recovery after permissions/payment/authorization are fixed. Both snapshot age and next_poll_at gate that demand; a missing first snapshot cannot bypass the cooldown. Failure persistence uses an independent bounded context so an expired page timeout still saves retry/terminal state.

`GET /api/v1/activity/view/problems` returns `collecting` and `refresh_after` (Unix seconds). Before the first publication it returns200 with `snapshot_at:0`, empty counts, and `collecting:true`; zero is not a verified count. During a later collection counts/snapshot_at keep the last complete publication. `stale` means seven-minute age or collection error. When idle refresh_after is the earliest request-driven refresh; while collecting it is the next durable collection step, not a promise of completion.

The frontend polls only while its tab is visible. Hiding the tab cancels its timer and in-flight request without discarding the published counts; returning to the tab immediately rechecks the source. During collection it waits until refresh_after with a minimum status interval of 10s, so a 60s batch pause or longer Retry-After does not cause 10s status reads. When idle it waits until refresh_after, bounded to 10s..7min to avoid one-second polling under clock skew; transport errors retry after 30s. A stopped initial collection displays an error rather than an endless loading spinner. Unmount cancels its timer/request. The frontend's day-event and missed-call polling remains independent. Several tabs can do cheap status reads but share the same scan. This is a completed local generation, not an amoCRM atomic point-in-time transaction: upstream mutations during pagination can still require the next refresh.

Migration034 is additive and leaves the obsolete requested_until column for compatibility with the old process between migrate and deploy. New code ignores its former30-minute subscription completely. Retire the column only in a later contract migration after all processes have upgraded.

Numbered upstream pagination remains a known consistency limitation. The documented leads ID filter accepts specific IDs, not an ID range ([filters](https://www.amocrm.ru/developers/content/crm_platform/filters-api)); tasks likewise document an ID or list, not an after-ID cursor ([tasks](https://www.amocrm.ru/developers/content/crm_platform/tasks-api)). Do not substitute an undocumented `filter[id][from]` as a guaranteed cursor. Keyset pagination or a reconciliation collector requires separate upstream validation.
