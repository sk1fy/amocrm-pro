# Контракт Platform V1

[OpenAPI](../api/platform-v1-openapi.yaml) описывает закрытый API для
`amocrm-pro-admin`, доставку lifecycle из Core и публичную проверку доступа
виджета. Core владеет этой схемой. Для A02 закрепите в Admin ревизию схемы
и прогоняйте общие примеры в тестах потребителя. Технические Core API,
Team OS и существующий widget auth продолжают работать по своим контрактам.

## Идентификаторы и жизненный цикл

`amo_account_id` и ID пользователей amoCRM передаются десятичными строками
в диапазоне положительного int64. `account_id`, `product_id` и ID эпизода
создаёт Platform. `integration_id` и `core_installation_id` создаёт Core.
Домен и имя аккаунта могут измениться. `product_code` неизменяем.
Публичный access принимает внешний ID amoCRM. В закрытом API `{id}` в
пути аккаунта означает UUID Platform.

Core выделяет монотонные `sequence` и `generation` на один
`core_installation_id` в транзакции подтверждённого перехода и outbox.
У первого install поколение 1 и sequence 1. Reinstall увеличивает
поколение после подтверждённого uninstall. Любое событие потока
увеличивает sequence. Источник evidence и его ссылка указывают на
подтверждённый OAuth либо результат uninstall. Выданный ранее срок
сохраняется на паре account/product при повторной авторизации и переустановке.

| Событие | Предусловие | Результат |
| --- | --- | --- |
| `installed` | Core подтвердил OAuth, происхождение первой установки проверено | Platform открывает эпизод и применяет начальную политику выбранного продукта |
| `reauthorized` | Подтверждён OAuth текущего эпизода | Platform сохраняет эпизод, поколение и срок |
| `uninstalled` | Core подтвердил удаление текущей установки | Platform завершает эпизод и прекращает доступ для его поколения |
| `reinstalled` | Предыдущее поколение завершено, новый OAuth подтверждён | Platform открывает новый эпизод с новым поколением и сохраняет прежний срок |
| `authorization_changed` | Core подтвердил смену эффективного статуса установки | Platform обновляет авторизацию текущего поколения и сохраняет эпизод и срок |

Platform отвечает `202` после записи в inbox. Повтор с тем же `event_id`
и телом возвращает тот же receipt. Иное тело для того же UUID или занятой
позиции `(core_installation_id, sequence)` даёт `409`. Пропуск перед
новым событием ставится на сверку. После закрытия пропуска Platform
применяет подтверждённые переходы по порядку. Позднее старое поколение
не меняет текущее. Примеры для доставки и повторов лежат в
[fixtures](../api/testdata/platform-v1).

OAuth upsert сохраняет технический UUID и обновляет счётчики токенов и Task
Control. Эти счётчики имеют другой жизненный цикл. Технический revoke
означает `reauth_required`. Disable интеграции или установки публикует
изменившийся статус для каждой затронутой установки из области Platform.
Частичный uninstall отправляется на сверку. Если технический переход
меняет доступность, он публикует статус через `authorization_changed`.
Событие не меняет `last_lifecycle_event`. Авторизационные переходы,
в том числе успешный OAuth, сохраняют свой номер события как
`authorization_sequence`. Для нового proof нужна авторизация
`authorized`. При отзыве или новой авторизации локальная проекция
перестаёт принимать proof с прежним `authorization_sequence`.

Для сверки и импорта Core публикует
[`CoreInstallations.GetSnapshot`](../api/proto/platform_v1.proto) по gRPC.
Core проверяет identity Platform и узкий scope делегирования
`platform_installations/snapshot` для точной установки. Источник меняет
домен и авторизацию независимо от событий lifecycle. Отсутствие
`generation/sequence` означает, что история старой строки требует
сверки. Снимок не создаёт эпизод или trial. Текущий status,
`created_at` и `refreshed_at` сами по себе не доказывают первую установку
и не открывают trial.

## Контекст BFF

Admin проверяет фактический host, сессию audience `managers` и актуальные
grants. Browser API использует `/api/v1/managers`. `POST /auth/login` и
`GET /me` этого namespace возвращают `ManagerIdentity`. Данные о
технической роли туда не входят. `POST /auth/logout` завершает
менеджерскую сессию. Admin владеет схемой браузерного auth, CSRF,
сотрудниками и аудитом.

Для закрытого Platform API BFF сериализует `ManagerContext` в UTF-8 JSON,
кодирует base64url без padding и помещает в один заголовок `X-Platform-Actor`.
Приёмник принимает только end-to-end mTLS от разрешённого Manager BFF.
Запросы Core в inbox имеют отдельную mTLS identity. Входящий
`X-Platform-Actor` от браузера отбрасывается. Допустимый размер заголовка
4096 байт. `request_id` обязателен. `trace_id` передаётся при наличии.
В V1 `deadline_at` должен быть позже `issued_at` и не дальше 30 секунд
от него. Platform проверяет время с допуском в 5 секунд для будущего
`issued_at`, grant и область ресурса. Tenant и списки доступных ресурсов
выводятся на сервере. Используйте новый envelope с текущим снимком grants
при восстановлении вызова. A02 хранит монотонную `grants_version` на
сотрудника и читает её вместе с grants. A07 увеличивает её в транзакции
изменения доступа и отзывает сессии при полном отзыве доступа. Долгая работа с внешним эффектом повторно
проверяет полномочия и предусловия перед эффектом.

BFF сохраняет свой intent до dispatch. Мутация передаёт UUID
`Idempotency-Key` и UUID `command_id`; обе идентичности и нормализованное
тело сохраняются на повторе. Platform атомарно сохраняет область команды,
хеш тела, исход и эффект. Повтор возвращает прежний исход. Конфликт ключа,
scope либо версии получает `409`. При потере ответа BFF сверяется по
`command_id` и сохраняет исходный ключ. Для принятой асинхронной команды
`Operation.id` равен `command_id`. `GET /commands/{id}` под менеджерским
префиксом Platform возвращает receipt для синхронной или асинхронной
команды. Исходный субъект должен сохранять право на ресурс. BFF читает
операцию либо получает точный ответ синхронной команды повтором того
же запроса. `404` от receipt не подтверждает, что команда не в пути.
Повтор закрытого вызова допустим только с прежними ключом, command ID
и телом.
Для команд, основанных на прочитанном состоянии, используйте `If-Match`
с сильным ETag в форме `"42"`. Повтор известной команды возвращает исход
до проверки устаревшего ETag. Новый ключ со старым ETag получает
`409 version_conflict` с `current_version`, если объект доступен.

У списков лимит 25 по умолчанию и 100 максимум. Курсор привязан к
актуальной области доступа, сортировке, фильтрам и снимку. Общая сводка
использует те же фильтры и права. Неизвестный фильтр отклоняется с `400`.
`null`, пустой подтверждённый список, ноль и недоступность источника
различаются. Операции с `x-release-capability` монтируются только после
подтверждения соответствующего источника. Входы V2/V3 отсутствуют в схеме V1.

## Proof виджета

Core выдаёт proof на `POST /api/v1/widget/platform-access-proof` по действующему
Core widget admission. Запрос передаёт один свежий одноразовый JWT в
`X-Auth-Token` или в `Authorization: Bearer`. Core берёт `integration_id` и установку из проверенного
principal. `product_code` берётся из утверждённой привязки integration/product,
доставленной Core из того же manifest, который проверяет Platform. Браузер
не выбирает продукт для выдачи proof. Несогласованная привязка закрывает
выдачу, ответ `503 policy_not_configured`. Endpoint отвечает
`{proof, expires_at}` с `Cache-Control: no-store`.

Core выпускает короткий JWT с `alg=EdDSA` (Ed25519), `typ=JWT` и
разрешённым `kid` после существующего server-side admission виджета.
`ProofClaims` фиксирует issuer, audience, account, product, техническую
установку, поколение и `authorization_sequence`. `iat`, `nbf` и `exp` передаются в секундах Unix.
В тестовом контуре TTL до 5 минут. Platform проверяет фиксированный
алгоритм, ключ из локального набора, времена и точное соответствие scope
маршруту и проекции Core. Недействительный proof получает 401, чужой
scope получает 403, недоступная PostgreSQL получает 503.
При отключении Core или Gateway ранее выданный proof остаётся пригоден
в пределах срока, поколения и версии авторизации из проекции. Отозванный ключ
исключается из набора проверки. При ротации старый и новый публичные ключи
перекрываются до истечения действующих proof.

Ответ access отправляется с `Cache-Control: no-store`. Platform проверяет
`now < valid_until` при каждом запросе. При отзыве авторизации, uninstall или смене поколения
старый proof теряет доступ после обновления проекции. Измерьте задержку
этого перехода в P04. Тестовый срок proof и online-проверка действуют до
проверки интеграции и утверждения рабочих TTL, SLA отзыва и offline policy.
Секрет интеграции и OAuth credentials остаются в Core. Для активации
используется отдельный одноразовый proof эпизода, после согласования
телефона и согласия.

## Контур начальной загрузки

P10 получает подписанный ответственным состав запуска. Достаточен
утверждённый manifest версии партии с перечнем пар `amo_account_id` и
`integration_id`, проверенным сопоставлением с продуктами, источниками
собственных сроков, снимком UTC и watermark потока по установке.
В одной паре account/product допускается одна установка, из которой
Platform берёт доступ. Если каталог связывает продукт с несколькими
Core-интеграциями, коллизия в одном аккаунте отправляется на сверку. Для
исторических строк с неясным поколением или сроком manifest указывает
решение сверки. Первичное наблюдение статуса и legacy данные не имитируют
свежий install. После импорта применяются события после watermark. Повтор
той же партии не меняет сроки, идентичности и счётчики. Отчёт P10 сверяет
разрешённые пары, загруженные строки, отклонённые записи и отставание
потока перед открытием доступа.

До подтверждения рабочего списка и фактических источников импорт и
публичный access включаются только в тестовом контуре. Используйте
отдельную тестовую интеграцию и разрешённый аккаунт. Проверка выпуска A09
сравнивает настоящие записи пяти разделов с источниками и включает
restore, откат и регрессию действующих поверхностей.
