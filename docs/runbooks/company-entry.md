# Вход в компанию из виджета amoCRM

Три виджета используют один Core API и компанию, определённую TeamOS для аккаунта amoCRM. Установка виджета и продуктовые разрешения не означают существования компании. Вход доступен действующим администраторам CRM. Каждый входит под своей TeamOS учётной записью. Владелец назначается только при фактическом создании компании.

## Настройка

Миграция `000037` добавляет уникальное наблюдение `account_id → company_id`. TeamOS остаётся источником истины. В worker задаются `COMPANY_ENTRY_HTTP_ADDRESS` с loopback/private адресом, `COMPANY_ENTRY_TLS_PROXY=true`, `COMPANY_ENTRY_TEAM_OS_URL` с точным HTTPS origin gateway, `COMPANY_ENTRY_FRONTEND_ORIGIN` с точным HTTPS origin TeamOS, `COMPANY_ENTRY_TEAM_OS_TOKEN` с существующим provisioning credential и отдельный `COMPANY_ENTRY_SUBJECT_CHECK_KEY`. Ключи содержат не менее 32 символов. Не передавайте ключи в браузер.

Примеры маршрутизации находятся в `deploy/company-entry`. Публично открываются только два widget endpoint. Callback открывается на отдельном приватном HTTPS virtual host. Gateway TeamOS и company используют тот же callback key и URL по контракту TeamOS. Эти файлы являются примерами конфигурации и не устанавливаются автоматически.

## Повторы и отказы

Каждый запрос использует новый disposable JWT. JTI долговечно расходуется до вызова TeamOS. Потерянный ответ означает неизвестный результат. Новый клик с новым JWT разрешает тот же аккаунт и пользователя и выпускает новый одноразовый код. Постоянная привилегированная ссылка не возвращается. Код живёт 60 секунд, хранится в TeamOS только как hash и передаётся frontend во фрагменте URL.

После успешного вызова TeamOS Core сохраняет наблюдение до выдачи URL. При отказе этой записи URL не выдаётся. Новый status или вход восстанавливает наблюдение по TeamOS. Противоречащую ассоциацию нельзя перезаписать. Существующая ассоциация при отсутствующей компании показывает блокировку; Create не создаёт ей замену. Go никогда не создаёт новую компанию.

При обмене кода TeamOS проверяет точную исходную установку и живые права CRM через Core вне SQL-транзакции. Затем блокирует и повторно проверяет локальные записи до расходования кода и создания сессии. Гарантия прав относится к последнему наблюдению, а не к непрерывному мониторингу уже выданной сессии.

Для новой учётной записи нужен корректный email серверного CRM профиля. При его отсутствии изменения откатываются. Уже связанная активная identity сохраняет собственный профиль; сопоставления по email нет. Обычные сотрудники продолжают использовать персональные многоразовые ссылки из TeamOS.

## Проверки

`internal/companyentry` содержит HTTP проверки настоящего disposable JWT с PostgreSQL replay store, живых прав, межаккаунтной изоляции, отзыва установки, конкурентной ассоциации и отказа Core записи после remote commit. `internal/integration/amocrm/company_entry_test.go` проверяет декодирование серверного профиля. Используется существующий Docker-first `make integration-test`; новый пакет включён в integration image. Нужны изолированная БД с именем `*_test`, `TEST_DATABASE_RESET_ALLOWED=true` и все миграции. Результаты запуска и ручную приёмку фиксирует владелец задачи отдельно.
