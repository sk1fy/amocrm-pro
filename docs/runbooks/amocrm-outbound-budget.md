# amoCRM outbound budget: настройка аккаунта и диагностика перегрузки

Решение и обоснование: [ADR-0029](../adr/0029-outbound-budget-account-scope.md).

Исходящий трафик к Go API v4 ограничен двумя бюджетами. Каждый запрос
списывает оба.

| Бюджет | Ключ | По умолчанию |
| --- | --- | --- |
| Пара «аккаунт + интеграция» | `account_id` + `integration_id` | 7 rps |
| Аккаунт суммарно | `account_id` | 50 rps |

Модель — token bucket с глубиной 1: первый запрос после простоя уходит без
задержки, дальше допуски каждого бюджета разделены интервалом не меньше
`1/rate`. Граница token bucket — `burst + rate × длительность`; это не
счётчик календарных секунд. Поздние таймеры проходят повторную проверку
обоих текущих бюджетов перед допуском.

## Конфигурация

Все переменные читает процесс worker при старте. Изменение применяется
**только после перезапуска** worker; хранения в базе и перезагрузки на ходу
нет.

| Переменная | По умолчанию | Диапазон | Смысл |
| --- | --- | --- | --- |
| `AMOCRM_BUDGET_PAIR_RPS` | 7 | 0.1–50 | Базовый лимит пары |
| `AMOCRM_BUDGET_PAIR_BURST` | 1 | 1–100 | Глубина bucket'а пары |
| `AMOCRM_BUDGET_ACCOUNT_RPS` | 50 | 0.1–50 | Потолок аккаунта |
| `AMOCRM_BUDGET_ACCOUNT_BURST` | 1 | 1–100 | Глубина bucket'а аккаунта |
| `AMOCRM_BUDGET_ACCOUNT_PAIR_RPS` | пусто | до 1000 записей | Переопределение лимита пары по аккаунтам |
| `AMOCRM_BUDGET_REPLICAS` | 1 | только 1 | Несколько независимых владельцев не поддерживаются |
| `AMOCRM_BUDGET_MAX_WAIT` | 5s | 100ms–1m | Максимальное ожидание одного запроса |
| `AMOCRM_BUDGET_PAIR_WAITERS` | 64 | ≥1 | Очередь ожидания на пару |
| `AMOCRM_BUDGET_ACCOUNT_WAITERS` | 512 | ≥ пары | Очередь ожидания на аккаунт |
| `AMOCRM_BUDGET_PROCESS_WAITERS` | 4096 | ≥ аккаунта | Очередь ожидания на процесс |
| `AMOCRM_BUDGET_INACTIVE_TTL` | 5m | 1s–1h | Время жизни неактивной записи бюджета |
| `AMOCRM_BUDGET_MAX_ENTRIES` | 16384 | 64–1000000 | Предел числа записей бюджета |

Некорректное значение не запускает worker: процесс завершается с сообщением,
называющим переменную и допустимый диапазон.

## Повышенный лимит для аккаунта с расширенным API-пакетом

Переопределение задаётся для `account_id` и действует на **все** интеграции
этого аккаунта. Потолок аккаунта остаётся 50 rps и не повышается.

```sh
# Аккаунт 1234567 купил пакет на 20 rps, аккаунт 7654321 — на 15 rps.
AMOCRM_BUDGET_ACCOUNT_PAIR_RPS="1234567:20,7654321:15"
```

Применение в локальном Compose-стенде:

```sh
docker-compose stop worker
docker-compose up -d worker
```

Проверьте отсутствие ошибок конфигурации в логе worker сразу после старта.
Значение выше `AMOCRM_BUDGET_ACCOUNT_RPS` отклоняется. Перезапуск создаёт
новые бюджеты с начальным запасом; история предыдущего процесса не сохраняется.

## Что происходит при перегрузке

1. Запрос получает общее время списания для пары и аккаунта. После
   пробуждения оба текущих бюджета проверяются и списываются атомарно.
2. Если слот дальше `AMOCRM_BUDGET_MAX_WAIT` или очередь соответствующего
   уровня заполнена, запрос **не идёт** в amoCRM и получает ошибку
   `overloaded` (`ErrorOverloaded`, retryable).
3. Пользовательские операции получают `resource_exhausted` с `Retry-After`.
4. Фоновые задачи получают retryable-ошибку и повторяются существующим
   механизмом задач с экспоненциальной задержкой и jitter.
5. Отмена контекста или наступивший дедлайн прекращают ожидание, возвращают
   будущие плановые списания и освобождают слот очереди.

Существующие слоты сохраняются; другие пары могут занимать свободные
промежутки бюджета аккаунта. Глобальный FIFO и равное деление 50 rps не
гарантируются. Позднее пробуждение может изменить порядок фактических
допусков; каждый вызов ограничен временем ожидания и deadline.

## Диагностика

Метрики worker (`/metrics`):

- `amocrm_budget_waiting` — сколько вызовов ждут прямо сейчас. Устойчиво
  высокое значение означает постоянную перегрузку.
- `amocrm_budget_wait_seconds{outcome="admitted|canceled|deadline_exceeded|overloaded"}`
  — время ожидания и исход.
- `amocrm_budget_rejected_total{scope="pair|account|process|wait|registry"}` —
  причина отказа: заполнена очередь пары, аккаунта, процесса, слот дальше
  `MaxWait` или исчерпан реестр записей.
- `amocrm_budget_throttled_total{scope="pair|account"}` — какой бюджет
  задерживает допуск. Рост только `pair` — упирается конкретная интеграция;
  рост `account` — упирается потолок 50 rps.
- `amocrm_requests_total{outcome="429"}` — amoCRM всё равно вернул 429; это
  возможно, потому что сторонние приложения аккаунта расходуют тот же бюджет.

`account_id` и `integration_id` в метки не попадают. Чтобы разобрать
конкретный аккаунт, используйте структурные логи по идентификатору запроса.

Типичные решения:

| Наблюдение | Действие |
| --- | --- |
| `throttled{scope="pair"}` растёт, `account` — нет | Проверить, оправдан ли объём работы этой интеграции; при купленном пакете задать переопределение |
| `throttled{scope="account"}` растёт | Аккаунт упирается в 50 rps; повышение лимитов пар не поможет, нужно снижать спрос |
| `rejected_total{scope="wait"}` растёт | Спрос устойчиво выше доступной скорости; проверить фоновые задачи и их повторы |
| `rejected_total{scope="registry"}` не ноль | Поднять `AMOCRM_BUDGET_MAX_ENTRIES` или проверить всплеск числа аккаунтов |
| `requests_total{outcome="429"}` не ноль при соблюдении локальных лимитов | Бюджет аккаунта расходует внешнее приложение; наши повторы уже учитывают `Retry-After` |

## Несколько процессов

Бюджеты живут в памяти процесса. Владелец исходящего трафика один — worker
(Gateway). Несколько владельцев не поддерживаются:
`AMOCRM_BUDGET_REPLICAS` должен быть равен 1. Значения больше одного
отклоняются, поскольку деление RPS не обеспечивает разделение общего
начального запаса. Для нескольких владельцев нужен общий координатор.
Оператор должен обеспечить единственную реплику worker/Gateway;
process-local limiter не обнаруживает другие процессы автоматически.

CLI `cmd/integrations` — отдельный короткоживущий процесс с собственным
limiter. Его трафик не координируется с worker, поэтому совместный потолок
для одновременной работы CLI и worker не гарантирован.
