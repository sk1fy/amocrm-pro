# Контроль активности 2.0: план переноса веб-панели на React

**Scope от 2026-10-26:** Telegram исключён из текущего этапа и отложен. Упоминания ниже описывают старую систему и прежний аудит, а не задачу текущей реализации.

Дата обновления: 2026-10-26. Статус: **backend/API и React adapters C2–C8 реализуются локально; Telegram отложен; production не обновлялся**. Итоговая матрица ниже отличает контракт от подключения устанавливаемого виджета. Предыдущий аудит сохранён в [activity-v2-audit.md](activity-v2-audit.md).

Документ фиксирует объём и порядок работ. Он не изменяет действующие
ADR/API и не подменяет backlog в GitHub Issues.

## 1. Зафиксированные решения пользователя

Эти решения приоритетнее прежних формулировок документа.

1. Отдельная веб-панель на React + TypeScript, сборка Vite.
2. Сначала переносится весь существующий функционал панели
   в новое оформление.
3. Целевой backend — amocrm-pro, его можно дополнять под продукт.
   Laravel и Vue — источники поведения; их ограничения не
   ограничивают новую систему. Runtime-зависимости от Laravel нет.
4. Неделя и месяц сейчас не реализуются: ни расчётов, ни графиков,
   ни сравнений, ни API. Переключатель День/Неделя/Месяц виден,
   рабочий — только дневной сценарий.
5. Устанавливаемый виджет amoCRM (оболочка, таймер, DOM-наблюдатели,
   callbacks) — после панели. Операторские веб-экраны и отображение
   истории задач/Imbox относятся к панели и нужны сейчас.
6. Максимальная глубина истории — один месяц.
7. Все экраны настроек пока внутри React-панели; интеграция с TeamOS
   позже и сейчас не разрабатывается.
8. Формы, модели настроек и API-слой отделены от оболочки для
   будущего переноса. Локальные предпочтения зрителя и общие
   настройки продукта различаются. Серверные секреты не попадают
   во frontend-сборку.

`sub-projects/amocrm-pro-activity-site` — тестовая зона backend,
не основа продуктовой панели; её назначение сохраняется.

## 2. Что есть и чего не хватает

| Основа | Состояние |
| --- | --- |
| Core | OAuth, авторизация, жизненный цикл установки, Gateway, бюджет запросов |
| CRM Events | Сбор, хранение, повторные проходы, enrichment, покрытие истории |
| Activity viewer | Панель по ключу ссылки, timeline/journal страницами ≤ 100, карточка события, coverage/freshness |
| Activity management | Создание, изменение (CAS), перевыпуск ссылки, справочник; только серверный токен |
| Период | ≤ 31 сутки, итоги за период, корзины hour/day/auto |

Чего не хватает для действующих функций (подробно — раздел 8
аудита): адрес CRM (C2),
проблемные списки CRM (C3), сессии задач/Imbox (C4), расширенные
настройки панели (C5), панель задач (C6), браузерная
admin-авторизация (C7), горизонт месяц (C8).

C1 реализован локально: `call_facts` в некомпактной ленте/журнале и
карточке события. Развёртывание и проверка на реальной установке отдельно.

Отсутствие метода — задача дополнения Go backend, а не повод убрать
функцию из интерфейса.

## 3. Приложение

Каталог: `rakurs-widgets-new/rkrs_activity_panel/web-panel`.
Стек: React 19, TypeScript 5.9, Vite 8. UI-kit не используется:
компоненты написаны вручную на токенах нового макета.
Существующие приложения репозитория не затрагиваются.

Слои:

- оболочка и маршруты (`#/p/{view_key}`, сотрудник, оператор,
  пропущенные, настройки);
- модели домена и расчёты с отдельными эталонами поверхностей;
- API-адаптер amocrm-pro и источник синтетических данных;
- `src/settings/` — модели, формы и API настроек отдельно от оболочки.

Режимы данных:

| Режим | Поведение |
| --- | --- |
| `live` | amocrm-pro viewer API; блок без контракта показывает «источник не подключён» |
| `fixtures` | Только синтетические данные, постоянный видимый баннер |
| `hybrid` | Live там, где контракт есть, синтетика для недостающих; каждый синтетический блок помечен |

Fixtures — инструмент разработки, не доказательство живой интеграции.
Сессии задач/Imbox без явного источника не подменяются событиями CRM.

Слои настроек:

1. локальные предпочтения — localStorage по панели;
2. серверные настройки панели — через API (C5, C7);
3. глобальная панель задач — отдельный объект (C6, C7).

Management token в браузер не попадает. Для локальной проверки
допустим dev-only Vite proxy, подставляющий токен из env сервера.

## 4. Правила переноса расчётов

- Формулы поверхностей (строка dashboard, рейтинг профиля, анализ
  событий) не унифицируются; у каждой свой эталон.
- Исправления старых артефактов вносятся только как явные изменения
  правил F1–F10 из аудита.
- Даты и время — в timezone аккаунта. Сравнение версий — на одинаковых
  событиях, дате, настройках и времени отсечения; различия живых
  данных не считаются ошибкой переноса.
- Данные вне доступной истории показываются как недоступные,
  не нулями.

## 5. Очерёдность

| Этап | Работы | Готовность |
| --- | --- | --- |
| 1 | Каркас, маршруты, тема, модели, слой данных, режимы | Панель открывается; режим данных различим |
| 2 | Основной дневной экран | Отделы, поиск, сортировка, дата, KPI, таймлайны, сравнение, автообновление |
| 3 | Сотрудник и проблемные списки | Все блоки профиля и переходы |
| 4 | История задач/Imbox, операторы, пропущенные | Веб-режимы перенесены |
| 5 | Настройки внутри панели | Локальные, серверные, панель задач |
| 6 | Состояния, адаптивность, браузерная проверка пути | Загрузка, пусто, ошибка, частично, устарело, недоступно |

Backend дополняется небольшими частями под существующие функции:
контракт → backend → подключение React. Масштабная переработка
не предшествует интерфейсу.

## 6. Приёмка первого выпуска

- Все функции из матрицы аудита доступны в React.
- Расчёты сверены синтетическими эталонами по каждой поверхности.
- История ограничена месяцем и доступностью источника.
- Неделя/месяц видны, но выключены и не имитируют аналитику.
- Проверены отмена устаревших запросов, автообновление, ошибки,
  пустые и частичные результаты, недоступный источник.
- TypeScript, lint, production build и browser-сценарии пройдены.
- Подключённые к amocrm-pro и синтетические блоки перечислены явно.

## 6a. Состояние реализации (2026-10-26)

| Контракт | Локальная реализация | Оставшаяся приёмка |
| --- | --- | --- |
| C1 | `call_facts` уже существовал; операторские планы и пороги теперь сохраняются в panel options | Реальные входящие/исходящие/пропущенные звонки на одном тестовом аккаунте |
| C2 | Scoped CRM origin из Core/Gateway через RPC и viewer API, React использует доверенный HTTPS origin | Развёртывание и переходы по ссылкам |
| C3 | Core-owned generations leads/tasks, durable phase/page checkpoint, один bounded batch по 250, публикация только полного snapshot, SQL counts по сотрудникам/воронкам, stale/error metadata | Сверка с legacy фильтрами CRM и нагрузка больших аккаунтов; фиксированного ограничения на размер аккаунта нет |
| C4 | Activity-owned work/activity/pause intervals, idempotent commands, serialization per employee, stop по session_id, viewer-read, React mapping | Live producer подключён к SDK, задачам CRM, Imbox DOM и own-state; demo остаётся отдельным. Нужна проверка на контролируемом amoCRM аккаунте |
| C5 | panel options: воронки, операторы/планы/пороги, настройки отделов; сохранение CAS, RPC, viewer projection, справочник воронок/этапов и формы React | Живая проверка записи и независимости двух панелей |
| C6 | Общие task-panel settings установки: enabled, сотрудники, future tasks, related deals, priorities, revision CAS; отдельный API и React | Применение этих настроек настоящим устанавливаемым виджетом |
| C7 | Core выдаёт после widget JWT + live admin check 30-минутный opaque browser credential, хранит hash; каждый management request заново проверяет admin; frontend очищает fragment и держит credential в памяти | Кнопка входа подключена в новом widget-app. Refresh страницы требует повторного входа из виджета |
| C8 | Новые defaults 31/31, owner schema допускает initial31 и retention31; существующие stored settings не переписываются | Явная настройка/backfill для существующих установок, измерения объёма и coverage после загрузки |

Миграции Core: `000032_activity_browser_sessions`, `000033_activity_problem_snapshots`.
Activity: `000005_panel_options`, `000006_work_sessions`, `000007_monthly_history`.
CRM Events: `000009_monthly_initial_history`.
При downgrade monthly migrations требуется заранее вернуть настройки к старым диапазонам; SQL не сокращает историю молча.

Старт сессии атомарно закрывает предыдущий интервал сотрудника. Таймстемпы
серверные. Stop требует ID текущей сессии, чтобы запоздалый ответ другой вкладки
не закрыл новую работу. Work-интервалы старше8часов закрывает фоновый watchdog в момент наблюдения, без усечения длительности. Imbox/activity не ограничиваются этим watchdog.
Чтение постраничное, по 200 сессий: cursor привязан к scope/сотруднику/периоду; React догружает полный диапазон без потолка на число сессий. Закрытая session history хранится32дня. Receipts сохраняются для безопасного replay; их expiry/tombstone policy требует отдельной эксплуатационной доработки.

Проверка локальными fixtures, unit/DB/RPC tests не означает прохождение живой
приёмки. Demo fallback профиля по-прежнему помечен и не является источником
фактических метрик. Production и старый Laravel/Vue/widget не изменены.

## 7. Последующий этап: виджет amoCRM

Отдельным планом: оболочка, авторизация в amoCRM, таймер работы/пауз,
действия по задачам, сбор Imbox-сессий, DOM-наблюдатели, очистка при
destroy. Панель принимает эти данные через API-слой (C4) и не зависит
от внутреннего состояния виджета.

## 8. Миграция и выпуск

- Старая панель доступна на время сверки и пилота.
- Формат ссылок и настроек не меняется молча: соответствие схем —
  в адаптере и маршрутизации.
- Account ID, installation/integration UUID и ID панели различаются.
- OAuth и другие серверные секреты не попадают в сборку.
- Выпуск выборочный; откат возвращает прежнюю панель без удаления
  истории.
