# Activity: неделя и месяц (period-v1)

Статус: в работе, ветка `feat/activity-period-week-month` (amocrm-pro и rakurs-widgets-new).
Дата: 2026-11-06. Источник требований — утверждённый концепт «Контроль активности ·
Сводный вариант» (вкладки «Неделя»/«Месяц») и решения владельца продукта ниже.
Этот файл — **единый контракт** между backend (Activity) и web-panel.

## 1. Решения

| # | Решение |
|---|---|
| R1 | Рейтинг периода = Σ активных минут / Σ прошедших минут окна по учтённым дням (как в концепте), не среднее дневных процентов |
| R2 | Зоны CRM строятся из событий сотрудника (`crm_events`), без сессий виджета |
| R3 | Сырые события хранятся 33 дня (было 31). Больше — нельзя |
| R4 | Выходные как в концепте: неделя Пн–Вс; Сб/Вс без активных сегментов не учитываются в суммах и средних; будний день без событий учитывается с нулём |
| R5 | Окно — то же, что у дневного экрана (окно панели `display_window`, личное `workWindow` перекрывает) |
| R6 | «Все активности» = исходящие звонки + сообщения + исходящие письма + закрытые задачи + переведённые сделки (любая смена этапа, `lead_status_changed`, как на дневном экране) |
| R7 | Ничего не хранится дольше 33 дней — ни сырые события, ни агрегаты. Прошлый период доступен, только если все его дни в пределах 33 суток; иначе «нет прошлого периода». Для месяца сравнение с прошлым месяцем поэтому доступно лишь в первые дни месяца — принято владельцем продукта |
| R8 | Плитка «Переведённые сделки» = любая смена этапа (`lead_status_changed`), как на дневном экране |
| R9 | Пятая зона «Прочее CRM» для событий, не попавших в остальные зоны |
| R10 | Лучший/худший час ищутся по всем часам окна |

## 2. Факты дня (`DayFacts`) — хранятся, не зависят от окна и фильтра воронок

Строятся из событий сотрудника (`created_by`) за календарный день в timezone аккаунта.

### 2.1 Занятость минут 0..1439
Правило `dashboard-v1` (`internal/services/activity/activity_rating.go`): событие занимает
`[m, m+len)`, `m` = минута дня события (час*60+минута, секунды отбрасываются);
`len = ceil(duration/60)` для `incoming_call`/`outgoing_call` с известной длительностью > 0,
иначе 1. Часть интервала после 1440 отбрасывается (как в dashboard-v1 — события
учитываются по своему dayKey).

Каждая занятая минута хранит:
- `kind`: `call` (если минуту занимает событие-звонок) иначе `crm`;
- `zone` — максимальная по приоритету зона событий, занимающих минуту.

### 2.2 Зоны (приоритет сверху вниз)
| Код | Зона | Событие |
|---|---|---|
| `C` | Звонки | тип содержит `call` (как `isDashboardCall`) |
| `T` | Задачи | тип начинается с `task_` или `entity_type` ∈ {task, tasks} |
| `I` | Imbox | `entity_direct_message`, тип содержит `chat_message` или `sms` |
| `D` | Сделки | `entity_type` ∈ {lead, leads} |
| `O` | Прочее CRM | всё остальное (контакты, компании, покупатели, …) |

### 2.3 KPI — списки минут (а не числа), чтобы точно резать по окну и по «той же точке»
| Ключ | Предикат (как `KPI_PREDICATES` web-panel) |
|---|---|
| `outgoing_calls` | `type == outgoing_call` |
| `messages` | `type == entity_direct_message` или содержит `chat_message` или `sms` |
| `outgoing_mail` | `type == outgoing_mail` |
| `completed_tasks` | `type == task_completed` |
| `lead_status_changes` | `type == lead_status_changed` (любая смена этапа) |

Плюс `calls_without_duration` (звонки без известной длительности) и `coverage` дня.

### 2.4 Разбивка по набору воронок
Фильтр панели (как `filterByPipelines` / `ratingPipelineMatch`): нет выбранных воронок —
берётся всё; иначе событие без признаков воронки остаётся, с признаками — если хотя бы
одна воронка выбрана. Факты хранятся «срезами» по отсортированному набору ID воронок
события (пустой набор — отдельный срез). При чтении объединяются срезы, прошедшие
фильтр панели → результат идентичен фильтру по сырым событиям, а один агрегат
обслуживает все панели аккаунта.

## 3. Статистика дня (`DayStat`) — считается при чтении (факты + окно + отсечка)

- `range = [start_minutes, rangeEnd)`. `rangeEnd`: прошедший день — `end_minutes`;
  день с отсечкой (сегодня или «та же точка» в прошлом периоде) — правило dashboard-v1:
  `endHour = floor(end/60)`, `h = min(endHour, cut.hour)`, `rangeEnd = h*60 + (cut.hour == h ? cut.minute : 0)`.
  `elapsed = max(0, rangeEnd - start_minutes)`.
  Правило dashboard-v1 сохранено бит-в-бит: если отсечка попадает в час `floor(end/60)`,
  `rangeEnd` выходит за `end_minutes` (окно 09:00–18:00, отсечка 18:30 → 18:30; в 19:00 —
  снова 18:00). Такие сегменты входят в `active/call/elapsed/first/last/kpi`, но не в `hours`
  и не в строки `period-days`.
- Сегменты по 2 минуты от `start_minutes` до `rangeEnd` (последний может быть короче).
  Сегмент **активен**, если любая его минута занята; **звонок**, если любая минута `call`.
- `active = min(elapsed, activeSegments*2)` (точный паритет с dashboard-v1:
  `round(active/elapsed*1000)/10 == dashboardRating`; в порядке вычисления JS
  `round((active/elapsed)*100*10)/10`, как `roundedRating`, — от него зависят половинные значения).
- `call = min(elapsed, callSegments*2)`.
- `first` = начало первого активного сегмента; `last` = `min(конец последнего активного сегмента, rangeEnd)`; `null`, если активных нет.
- `idle_inside` = (неактивные сегменты между первым и последним активным) × 2.
- `hours`: для каждого часа `h` из `hours` ответа — `[active_h, call_h, elapsed_h]`.
  Сегмент целиком относится к часу своего начала (`active_h` += 2 или длина укороченного
  сегмента); `elapsed_h` = минуты `range`, попавшие в час. Доля часа на клиенте
  ограничивается 1.
- `kpi` = число минут из списков §2.3, попавших в `range` (после фильтра воронок):
  массив в порядке `[outgoing_calls, messages, outgoing_mail, completed_tasks, lead_status_changes]`.
  `events` = сумма пяти.
- `counted` = день не в будущем И НЕ (Сб/Вс без активных сегментов в range).

## 4. Период

- Неделя: Пн–Вс, `anchor` — любой день недели. Месяц: календарный.
- Состояния дня: `future`, `today` (отсечка `cutoff_unix`), `ready`, `pending` (агрегат ещё
  считается), `unavailable` (истории нет).
- «До той же точки»: только если текущий период содержит сегодня.
  `cut = {day_index: индекс сегодняшнего дня в периоде, minute: минута cutoff в timezone}`.
  Неделя — индекс дня недели; месяц — `день месяца - 1`. В прошлом периоде: дни с
  индексом `< day_index` — целиком, день `day_index` — с отсечкой `minute`, позже — не
  входят. Если `day_index >= len(previous.days)` (прошлый месяц короче) — `cut = null`
  (прошлый период целиком). Прошедший (не текущий) период сравнивается с предыдущим целиком.
- `previous.available = true`, только если все дни прошлого периода в состоянии `ready`.
  Иначе — «нет прошлого периода», частичных сравнений нет.
- Рейтинг = `Σactive / Σelapsed` по `counted` дням; `null`, если `Σelapsed == 0`.

## 5. API

### 5.1 `GET /api/v1/activity/view/period` (viewKey)
Query: `kind=week|month` (обяз.), `anchor=YYYY-MM-DD` (обяз.), `start_minutes` 0..1439,
`end_minutes` 1..1440 (обяз., `end > start`), `cutoff_unix` (опц.; без него — время
сервера; используемое значение возвращается), `employee_ids` (опц., как у `/view/activity`,
≤ 100; по умолчанию все сотрудники панели).

Клиент запрашивает сотрудников пачками по 25 (лимит ответа 3 МБ).

```json
{
  "formula_version": "period-v1",
  "kind": "week",
  "timezone": "Europe/Moscow",
  "start_minutes": 540,
  "end_minutes": 1080,
  "cutoff_unix": 1793000000,
  "snapshot_at": 1793000005,
  "history_from": "2026-08-01",
  "refresh_after": 1793000065,
  "hours": [9, 10, 11, 12, 13, 14, 15, 16, 17],
  "current":  { "start": "2026-11-02", "end": "2026-11-08", "days": ["2026-11-02", "..."] },
  "previous": { "start": "2026-10-26", "end": "2026-11-01", "available": true,
                "cut": { "day_index": 3, "minute": 940 } },
  "employees": [{
    "employee_id": 7,
    "current":  { "rating": 0.47, "days": [ <DayStat> ] },
    "previous": { "rating": 0.44, "rating_full": 0.45, "days": [ <DayStat полные> ], "cut_day": <DayStat с отсечкой> }
  }]
}
```

- `cutoff_unix` возвращается всегда (переданный или серверное время).
- `previous` верхнего уровня, как и `current`, содержит `days` (список дат прошлого периода).
- `history_from` = позднейший из «сегодня − 32 дня» (сервер) и первого целого дня, который
  ещё хранит CRM Events (`SyncStatus.HistoryFrom`) — самый ранний день, по которому есть данные (не глубже 33 суток);
  клиент ограничивает навигацию назад: период можно открыть, если его последний день
  не раньше `history_from`; дни до `history_from` приходят как `unavailable`.
- `refresh_after` — есть только если хоть один день `pending`.
- `previous` у сотрудника — `null`, если `previous.available == false`.
  `previous.rating` — с учётом `cut` (дни `< day_index` + `cut_day`); `rating_full` — весь период.
  `cut_day` — `null`, если `cut == null`.

`DayStat`:
```json
{ "day": "2026-11-02", "state": "ready", "counted": true, "coverage": "verified", "partial": false,
  "kpi": [12, 30, 2, 9, 1], "events": 54,
  "active": 312, "call": 95, "elapsed": 540, "idle_inside": 120,
  "first": 548, "last": 1062,
  "hours": [[40, 12, 60], [52, 20, 60]] }
```
Для `future`/`pending`/`unavailable` — только `day`, `state`, `counted:false`.
`partial` — день посчитан по неполным событиям. Этап 1: каждый день читается отдельным
запросом (полночь → конец окна + 1 час, для «сегодня» — до `cutoff_unix`), не больше 60 страниц
по 100 событий на пачку сотрудников, 4 дня параллельно, общий бюджет сканирования 20 с
(дедлайн запроса 25 с, delegation ~30 с). Упор в страницы или бюджет → `partial`, а не ошибка.
Звонки без длительности, как у рейтинга, дочитываются карточками событий: ≤ 150 на запрос,
сначала новые дни; не дочитанные к концу бюджета делают день `partial`.
Дни прошлого периода читаются, только если все они в пределах 33 суток.

Ошибки — как у остальных `/view/*` (`ActivityShareError`): 400 на неверные параметры,
404 вне панели, 429, 503.

### 5.2 `GET /api/v1/activity/view/employees/{employeeId}/period-days` (viewKey)
Query: `from_day`, `to_day` (YYYY-MM-DD, ≤ 31 день), `start_minutes`, `end_minutes`,
`cutoff_unix` (опц.). Для «Сравнения рабочих дней», грузится лениво.

```json
{
  "formula_version": "period-v1",
  "timezone": "Europe/Moscow",
  "start_minutes": 540, "end_minutes": 1080, "segment_minutes": 2,
  "days": [{
    "day": "2026-11-02", "state": "ready", "first": 548, "last": 1062,
    "kinds": "0011220000…",
    "zones": "--CCTT--DD…"
  }]
}
```
Ответ также содержит `employee_id`, `cutoff_unix`, `snapshot_at`, `history_from`, а день в
состоянии `ready`/`today` — `coverage` и `partial` (как в §5.1). Фильтр воронок — фильтр панели.
`kinds`/`zones` — по одному символу на 2-минутный сегмент окна (`ceil((end-start)/2)`):
`kinds`: `0` пауза, `1` CRM, `2` звонок, `.` ещё не наступило;
`zones`: `-` нет событий, `C/T/I/D/O` по §2.2, `.` ещё не наступило.
Для `future`/`pending`/`unavailable` — только `day`, `state`.

## 6. Backend (Activity)

- Хранение 33 дня: `serviceapi/settings.go` (default retention 33, граница ≤ 33),
  `services/crmevents/service.go` (та же граница), миграции activity и crmevents
  переводят существующие установки 31 → 33. `InitialDays` ≤ 31, лимит запроса 31 день
  и backfill ≤ 31 день не меняются.
- Модуль `period_facts.go`: `BuildDayFacts`, `DayStatFrom(facts, window, cut, pipelines)`,
  сегменты для `period-days`. `dashboardRating` должен давать тот же результат (тест паритета).
- Этап 1 (обязательный, реализован): всё считается на лету из сырых событий; по дню — тот же
  ограниченный скан страниц, что у рейтинга (→ `partial` при упоре в лимит, см. §5.1).
  Состояние `pending` в этом режиме не используется. События читаются **delegation зрителя**
  (`UserGrantsFor(activity, view)` уже содержит `events/read`), как у `/view/activity`.
  Между Core и Activity — gRPC `ViewActivityPeriod`/`ViewActivityPeriodDays`: запросы
  типизированы, ответы передаются JSON-документом публичного контракта.
- Этап 2 (только скорость, R7 — не история; **не реализован, follow-up**): кэш фактов закрытых дней
  `activity_day_facts` (installation, integration, employee, day, timezone,
  formula_version, slices, coverage, calls_without_duration, final, computed_at),
  PK `(installation_id, employee_id, day)`, хранение **33 дня** (как сырые события).
  Заполняется по требованию (≤ 3 дня за запрос, остальные — `pending` + `refresh_after`)
  и/или фоновым сборщиком. Открытый вопрос: system-доступ к событиям сейчас невозможен —
  `corepolicy.Issue` разрешён только Core/Events, а system-гранты не включают `events/read`;
  фоновому сборщику в Activity нужно решение (ADR) по политике. Заполнение по требованию
  может использовать delegation зрителя, как этап 1.
  Пересчёт D на D+1…D+3; `final`, когда coverage verified и нет звонков без длительности.
  Смена formula_version или timezone — пересчёт.
- «Сегодня» всегда считается на лету.

## 8. Блоки (формулы концепта)

Σ — по выбранным сотрудникам и `counted` дням; prev — прошлый период «до той же точки».

1. **Итоги**: Исходящие звонки (kpi[0]), Закрытые задачи (kpi[3]), Переведённые сделки (kpi[4]),
   Все активности (events), Письма (kpi[2]), Рабочее время (Σactive), Простой (Σidle_inside,
   рост — плохо). Дельта `(cur-prev)/prev`; оба 0 — «без изменений»; prev 0 и cur > 0 — +100%;
   «было X»; «нет прошлого периода». «Прошло дней: N» = max числа counted дней среди сотрудников.
2. **По часам**: строки — сотрудники по рейтингу; колонки — `hours`. «Уровень» = среднее по
   counted дням с `elapsed_h > 0` от `min(1, active_h/elapsed_h)`; «Звонки» — то же для `call_h`;
   «Δ» = уровень текущего − уровень прошлого (prev **целиком**), в п.п. ▲/▼ — лучший/худший час
   (худший — среди уровней > 0). Колонка «Рейтинг» + Δ п.п. к prev.rating. Итоговая строка —
   среднее по сотрудникам; её рейтинг — среднее рейтингов.
3. **Сотрудники**: Σactive, Σevents, рейтинг, % к prev; сортировка по Σactive; полоса — от максимума.
4. **Динамика** (звонки kpi[0], закрытые задачи kpi[3]): по индексу дня сумма по выбранным; будущий
   день — `null`; prev — **целиком**, пунктир. Ось: «Пн 3» (неделя) / «3» (месяц).
5. **Сравнение рабочих дней** (на сотрудника; порядок — по рейтингу; первые 2 раскрыты):
   чипы дней (будущие недоступны; «N событий» / «нет событий» / «идёт»); по умолчанию
   прошедшие Пн–Пт. По выбранным дням с активностью: медиана first, медиана last,
   разброс = max(last) − min(last), Σactive, Σevents. Строка дня: полоса (режимы «Зоны CRM» /
   «Активность и паузы»), Первое, Последнее, Активность, События, «Открыть день».
   Повторяющиеся паузы: ≥ 2 дней с активностью; A = min(first), B = max(last); для каждого
   сегмента — число дней, где он пауза и лежит внутри [first,last] этого дня; порог
   `max(2, ceil(0.6 × дней))`; пауза = подряд ≥ 8 сегментов (16 минут).
