# ADR-0044: переключение и возврат продукта с сохранением данных и операций

Дата: 2026-10-22. Статус: **Proposed — готово к review ПВ-01**.
Задача: [ПВ-01.06](https://app.clickup.com/t/1amkccgbvj5).
Результат — обязательный шаблон волны миграции; боевых переключений ПВ-01 не выполняет.

## Решение и область

Перенос выполняется по account+product, для Activity — только по заранее
разделённой функции. [ADR-0040](0040-product-routing-ownership.md) определяет
epoch, source fence, quiesce ACK и активацию target. Этот ADR определяет данные,
остаток работы, критерии пилота и обратный путь. Новый продукт на Core проходит
onboarding, а не фиктивную миграцию пустой старой установки.

Рабочие точки опоры: [ADR-0023](0023-product-module-physical-transfer.md)
разделяет возврат процесса и перенос БД;
[ADR-0034](0034-distribution-durable-assignment-evidence.md) запрещает считать
совпадающий GET доказательством авторства внешнего изменения;
[SSD настройки](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Actions/Widget/SettingsGroupAction.php)
и [цвета сделок](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/Modules/Widgets/ColorLeads/Models/RkrsColorLead.php)
показывают, что даже первый пилот содержит пользовательские данные.

## Паспорт волны до разработки

Для каждого продукта исполнитель сохраняет в его спецификации:

| Поле | Что требуется |
| --- | --- |
| Scope | Canonical product/function, cohort аккаунтов, интеграции и соответствия legacy ID |
| Функции | Сохраняем/меняем/исключаем, доказательства использования, решение владельца для исключений |
| Версии | SHA Core, SSD, TeamOS при участии, ZIP/bundle hash, совместимые версии контрактов и схема данных |
| Источники исполнения | HTTP, вебхуки, DP, Salesbot, cron, daemon, queue, browser direct mutations |
| Права | Пользовательские/служебные роли, установочные grants, домены, OAuth-owner и rotation path |
| Объём | Число записей, оценка времени остановки/импорта/обратного переноса на измеренном объёме |
| Приёмка | Сценарии, ожидаемые результаты, наблюдение, пороги остановки и ответственный оператор |
| Возврат | Обратные преобразования, граница необратимости, что делать с unknown внешними эффектами |

Метрики использования не доказывают отсутствие потребителей при пробелах
телеметрии. Неиспользуемая по метрикам функция исключается только после
проверки покрытия и решения владельца. Полная перепись старых возможностей
не заменяется перечислением HTTP-контроллеров.

### Таблица данных — заполняется для каждой сущности

| Сущность | Источник/ключ | Target/ключ | Transform/version | Сверка | Изменения во время переноса | Возврат/архив |
| --- | --- | --- | --- | --- | --- | --- |
| Установка и права | account+canonical product, история установки | Core installation/generation и SSD mirror | явная mapping table | соответствие, статус, поколение | versioned lifecycle events | сохраняются original commercial identity и trial history |
| Настройки | legacy settings key + schema | product-owned settings | проверяемый transformer | canonical digest и семантические примеры | source freeze либо watermark с финальной дельтой | обратный transformer обязателен |
| Данные продукта | например, account+lead для цветов | product-owned rows | ID-map при необходимости | counts по scope, ключи, digest, выборочная UI-сверка | зафиксированная граница после quiesce | перенос новых изменений обратно |
| Правила автоматизаций | rule_index/handler_name, saved URLs | прежний ID либо mapping | версия адаптера | реальное событие из существующего правила | ingress сохраняет принятую работу | прежние ссылки продолжают разрешаться |
| Операции/очередь | stable source operation/event identity | operation ledger + pending work | outcome mapping | pending, dispatched, succeeded, uncertain сверены раздельно | single-owner protocol | completed не запускаются повторно |
| История/панели | источник с retention и правами | перенос либо сохранённый legacy reader | явно указанный режим | доступ старой ссылки/истории | определить, продолжается ли сбор | срок и способ сохранения доступа |

Counts сами по себе недостаточны: одинаковое число строк не подтверждает
правильные значения и связи. Сверка выполняется по account/product и ключам,
включая null, удалённые значения, даты/часовые пояса, неизвестные CRM ID и
дубликаты. Даты оплаты и trial не вычисляются заново из момента импорта.

### Таблица операций с внешним эффектом

| Тип | Operation identity | Что сохраняем до HTTP | Как подтверждаем исход | Действие при unknown | Переключение/возврат |
| --- | --- | --- | --- | --- | --- |
| Изменение существующей CRM-сущности | source event + rule/episode + entity | intent, payload hash, epoch, credential identity | проверенный ACK и достаточные evidence продукта | не повторять автоматически; сверка по контракту | scope ожидает разрешения unknown |
| Создание сделки/строки/уведомления | идентичность бизнес-операции, не случайный retry ID | intent, payload, ключи внешней корреляции если поддержаны | внешний ID/ACK; отдельная проверка допустимого поиска | duplicate-safe API либо ручной разбор; отсутствие доказательства не значит failure | нельзя просто перенести как новую pending job |
| Локальные настройки | account/product + command ID | request hash и expected settings revision | атомарная запись с receipt | повтор возвращает receipt | переносятся receipt и актуальная revision |

В таблице фиксируется конкретный метод для каждой операции продукта. Нет
общей гарантии exactly-once внешнего API. Явное разрешение повторить неизвестный
эффект с риском дубля требует продуктовой политики и аудита; оно не считается
безопасным автоматическим восстановлением. Для пилота по умолчанию unknown
останавливает перенос соответствующего scope.

## Порядок переключения

1. **Подготовка.** Проверить паспорт, backup и восстановление на отдельной
   среде, mappings, совместимость старых URL/вкладок, продуктовые права,
   возможности обратного преобразования и [общий бюджет](0043-hybrid-amocrm-outbound-budget.md).
   Настроить мониторинг/оператора; target установлен, но его исполнение закрыто.
2. **Предварительный импорт.** При большом объёме скопировать снимок с
   watermark, сохраняя source единственным writer. Повтор импорта идемпотентен;
   source identity не меняется. Для небольшого пилота допустим весь импорт
   после freeze. Не вводить двустороннюю запись пользовательских настроек.
3. **Freeze.** Создать transfer с expected_revision. Source сохраняет fence,
   останавливает новые мутации и подтверждает все пути исполнения. Уже
   принятые операции явно завершаются либо передаются с неизменной identity;
   unknown не маскируется истёкшим lease. Новые входящие события сохраняются
   в durable inbox до ACK. Неограниченный drain под постоянным ingress запрещён.
4. **Финальная дельта.** После quiesce зафиксировать source boundary, перенести
   изменения/удаления и operation ledger; проверить таблицу данных. В этот
   момент запись продукта запрещена на обеих платформах. Пользовательские
   изменения не принимаются как якобы успешно применённые.
5. **Подготовка target.** Сверить OAuth ownership по
   [ADR-0039](0039-widget-migration-oauth-ownership.md), установку/права, свежий
   entitlement по [ADR-0042](0042-core-ssd-billing-adapter.md), вебхуки,
   очередь и источники данных. Зафиксировать prepare receipt с хешами сверки.
6. **Активация.** Core коммитит новый owner/epoch только с source и target
   receipts. Target подтверждает актуальную запись и открывает исполнение.
   Обновление браузерного маршрута следует этому решению; source остаётся
   fenced, включая после рестарта. Для платных пилотов применяется явная
   согласованная политика наблюдения/доступа, а не неявное обходное разрешение.
7. **Проверка.** Выполнить продуктовые сценарии, старую открытую вкладку,
   существующие автоматизации и повтор доставки. Проверить запись SSD,
   отсутствие новых trial/продаж при переносе и отсутствие старых мутаций.
   Сверить выполненные эффекты, принятую очередь, ошибки и задержки.

Смена DNS/ZIP сама по себе не является cutover. При смене интеграции отдельно
подтверждаются reauthorization, места встраивания и сохранённые правила. Пока
этого нет, «без перенастройки» не считается доказанным.

## События после финальной границы

Ingress нельзя считать частью однократного dump. Для source endpoint
сохраняется монотонный ingress_cursor и durable relay outbox. Принятие события
и запись его relay-направления/transfer_id происходят атомарно до внешнего ACK.
Граница B делит принятый inbox: записи до B сверены/переданы в финальном
импорте; записи после B доставляются отдельно. Переключение lane к relay
сериализуется с назначением cursor, поэтому между снимком и relay нет дырки.

Relay передаёт исходный source_event_id, operation identity, scope, cursor и
payload hash; новое transport delivery ID не создаёт новое бизнес-действие.
Target durable inbox дедуплицирует source identity и применяет продуктовую
семантику повторов amoCRM. Target может принять backlog в preparing, но
исполнение закрыто до active commit. Source удаляет relay-запись только после
сохранённого ACK target; timeout повторяет доставку, не внешний эффект.
Пропуски cursor сверяются явно; watermark ACK продвигается только по непрерывно
подтверждённой последовательности. Поздние события продолжают идти по relay,
пока старый URL обслуживает клиентов. Не требуется ждать прекращения ingress.

При отмене или возврате незавершённый relay передаётся текущему владельцу с
той же identity после проверки его inbox/operation ledger. Нельзя направить
неподтверждённое событие двум активным исполнителям. Тесты: событие между
source boundary и prepare, между prepare и activate, crash после target commit
до ACK, повтор и смена направления с непустым relay.

## Возврат

Возврат выполняется новым transfer_id и большим epoch. Сначала останавливается
текущий writer, разрешаются его in-flight/unknown операции, затем новые данные
и receipts переводятся в совместимый legacy формат и сверяются. Только после
этого SSD получает право исполнения. Старый snapshot без новой дельты не
восстанавливается поверх актуальных данных.

OAuth может остаться у Core: SSD вызывает согласованные типизированные CRM
операции через Core. Возврат продуктового owner не означает возврат старой
копии refresh token. Перенос credentials обратно — отдельный протокол ADR-0039.

Отправленные сообщения, созданные сделки и внешние записи не исчезают при
возврате. Их outcome/identity сохраняются; автоматическая компенсация не
вводится. Если обратный transformer отсутствует либо исход внешнего запроса
неизвестен, безопасное действие — остановка scope и восстановление вперёд,
а не включение старого writer. Такой продукт не проходит критерий проверенного
автоматического возврата до устранения ограничения.

## Критерии пилота и расширения

Технический первый пилот: собственный аккаунт demorkrs, его ID подтверждается
оператором, а не берётся из примерного JSON. Затем несколько явно выбранных
лояльных клиентов с разными объёмами и вариантами настроек.

Для каждого scope сохраняются фактические доказательства:

- все выбранные функции работают; настройки/данные/связи сверены;
- срок и основание доступа сохранены, новые коммерческие действия не возникли;
- Core и Filament показывают правильные owner, installation и sync-state;
- source не выполняет мутации при активном target, включая stale cache/restart;
- принятые операции не потеряны; completed не повторились; unknown показаны;
- существующие ссылки автоматизаций, обновление пакета и старая вкладка проверены;
- возврат после изменения данных на target и повторный переезд выполнены;
- пройдены перезапуск, недоступность источника/target, потеря ACK и события
  удаления/переустановки; соседние аккаунты не затронуты.

Стартовое предложение для наблюдения: не менее двух рабочих дней и одного
полного цикла самой редкой включённой автоматизации. Это минимум наблюдения,
а не доказательство объёмной нагрузки; для недельного задания нужны неделя
либо согласованный воспроизводимый эквивалент плюс контроль реального цикла.
Числовые SLO по задержке определяются паспортом продукта до переключения.

Немедленная остановка расширения: подтверждённая потеря/подмена данных,
двойное исполнение, доступ чужого аккаунта, неверная блокировка оплаченного
клиента или неподконтрольный рост unknown. Остановка scope не означает
автоматический возврат на SSD. Оператор сначала проверяет условия возврата.

Закрытие пилота подтверждает перечисленные аккаунты и версии. Оно не
подтверждает массовый перевод, модерацию или production других продуктов.
ПВ-05/ПВ-08 продолжаются после принятого ПВ-04 независимо от публичного
Распределения. Само Распределение проходит собственную приёмку новой установки
и Billing, без ожидания миграции старых клиентов.
