# ADR-0029: область действия исходящего бюджета amoCRM и поведение при перегрузке

Статус: принято 2026-09-18. Заменяет часть [ADR-0019](0019-gateway-outbound-budget.md):
ключ бюджета интеграции, модель всплеска и поведение при перегрузке. Решение
ADR-0019 о **единственном владельце** исходящего трафика сохраняется.

Не смешивать с бюджетом живой роли актёра ([ADR-0011](0011-activity-authorization-budget.md)),
ingress limiter виджета/webhook и fair claim очереди Core.

## Проблема

ADR-0019 хранил бюджет интеграции по `integration_id`. Одна интеграция,
установленная в двух аккаунтах amoCRM, делила один бюджет 7 rps: нагрузка
одного аккаунта снижала доступную скорость другого. Ожидание было
неограниченным: `rate.Limiter.Wait` парковал любое число goroutine, поэтому
очередь и память росли, пока держалась перегрузка.

## Решение

### 1. Ключ бюджета — пара [аккаунт, интеграция]

`budgetKey{AccountID, IntegrationID}` — 7 rps по умолчанию. Дополнительно
каждый аккаунт ограничен 50 rps. Оба бюджета списываются для каждого
исходящего запроса API v4. Число пользователей, установок, вкладок, задач и
воркеров не создаёт дополнительных бюджетов: ключ не содержит
`installation_id`.

### 2. Модель окна: token bucket, `burst = 1`

Обе ставки реализованы token bucket'ом `golang.org/x/time/rate` с глубиной
**один** токен. Это сознательный отказ от прежнего `burst = 7`: при глубине 7
на стыке секунд проходило до 14 запросов, что amoCRM считает превышением.
С `burst = 1` последовательные допуски каждого бюджета разделены
интервалом не меньше `1/rate`. Token bucket включает начальный токен:
его общая граница — `burst + rate × длительность`, а не строгий счётчик
календарных секунд. После пробуждения таймера оба текущих bucket'а
проверяются и списываются атомарно, поэтому позднее пробуждение не
сжимает запланированные слоты в неограниченный всплеск.

`AMOCRM_BUDGET_PAIR_BURST` и `AMOCRM_BUDGET_ACCOUNT_BURST` позволяют поднять
глубину (1–100), если для конкретной установки измерения покажут, что amoCRM
допускает всплеск. По умолчанию всплеска нет.

### 3. Переопределение лимита — на аккаунт

Расширенный API-пакет покупает аккаунт, поэтому переопределение задаётся для
`account_id` и действует на **все** пары этого аккаунта:
`AMOCRM_BUDGET_ACCOUNT_PAIR_RPS="1234567:20,7654321:15"`. Потолок аккаунта
всегда остаётся 50 rps и переопределением не поднимается; конфигурация с
переопределением выше потолка отклоняется при старте. Отдельного
переопределения для одной пары нет: если оно понадобится, ключ карты
расширяется до пары без изменения остальной модели.

Настройки хранятся в конфигурации процесса и применяются **при перезапуске**
worker. Хранение в PostgreSQL с перезагрузкой на ходу не вводится (ADR-0001,
[ADR-0019](0019-gateway-outbound-budget.md)): пилот меняет лимиты редко, а
перезапуск worker уже является штатной операцией. Перезапуск создаёт новые process-local бюджеты с начальным запасом;
перезапуски не являются способом сохранения общего состояния лимитов.

### 4. Ограниченное ожидание и отказ

Ожидание ограничено с четырёх сторон:

| Предел | По умолчанию | Переменная |
| --- | --- | --- |
| Ожидающих на пару | 64 | `AMOCRM_BUDGET_PAIR_WAITERS` |
| Ожидающих на аккаунт | 512 | `AMOCRM_BUDGET_ACCOUNT_WAITERS` |
| Ожидающих в процессе | 4096 | `AMOCRM_BUDGET_PROCESS_WAITERS` |
| Время одного ожидания | 5 с | `AMOCRM_BUDGET_MAX_WAIT` |

Лимиты вложены: одна пара не может занять всю ёмкость аккаунта, аккаунт — всю
ёмкость процесса. Если очередь заполнена или слот дальше `MaxWait`, запрос
получает `*APIError{Kind: ErrorOverloaded, Retryable: true}` **без** HTTP.
Deadline вызывающего проверяется до парковки: если слот позже дедлайна,
возвращается `context.DeadlineExceeded` сразу, а не по истечении таймаута.

Отмена контекста прекращает ожидание, удаляет будущие списания из обоих
календарей и освобождает слот очереди. Уже прошедшие плановые времена
могут оставить консервативный расход; текущие bucket'ы не расходуются
до фактического допуска. Лимитер сам не делает повторов: фоновые задачи
получают `jobs.Retryable` и повторяются существующим механизмом задач с
экспоненциальным backoff и jitter (`jobs.Backoff`). Для перегрузки подсказка
`Retry-After` намеренно не проставляется в задачах, чтобы отказы не
синхронизировались.

Пользовательские операции получают `serviceapi.ResourceExhausted` с
`Retry-After` через `corepolicy.MapUpstreamError`; админ-команды
классифицируют перегрузку как `rate_limited`.

### 5. Порядок обслуживания — календарь доступных слотов

Существующие слоты не перемещаются новым запросом. Новая пара может
использовать свободные промежутки бюджета аккаунта: медленная пара не
блокирует весь аккаунт до своего последнего запланированного запроса.
Глобальный FIFO и равное деление 50 rps не обещаются. При позднем
пробуждении таймеров порядок фактического допуска зависит от планировщика;
ожидание ограничено `MaxWait` и deadline. Приоритетов пользовательских
операций перед фоновыми нет.

### 6. Два бюджета — общее время списания

Под одним мьютексом выбирается время, допустимое для обоих бюджетов.
Проверяется также сохранение уже назначенных будущих списаний: вставка
нового слота не должна лишить их разрешений. Оба календаря получают одно
время отправки. При отмене будущие списания удаляются, существующие слоты
остальных запросов сохраняются.

В момент допуска к HTTP текущие bucket'ы проверяются и расходуются
атомарно. Если таймер проснулся поздно и разрешений не хватает, запрос
продолжает ограниченное ожидание. Уже отправленный запрос учитывается
независимо от результата.

### 7. Специальные пути

- Повтор HTTP после обновления OAuth-токена: `DoJSON` вызывает `waitBudget`
  на каждой попытке, поэтому каждый фактический запрос расходует бюджет.
- Bootstrap: пока `account_id` неизвестен, используется ограниченный bucket
  пары `{account 0, integration}`; после определения ID канонические бюджеты
  пары и аккаунта списываются через `charge`, который не возвращает токены
  при отмене.
- `WithTokenProvider` сохраняет общий limiter: клиенты с разными
  TokenProvider не создают второй бюджет.
- Очистка неактивных записей (`AMOCRM_BUDGET_INACTIVE_TTL`, по умолчанию 5
  минут) удаляет запись только если на ней никто не ждёт **и** её bucket
  полностью пополнен. Пересоздание такой записи даёт ровно тот же запас,
  поэтому очистка не позволяет обойти ограничение. Число записей ограничено
  `AMOCRM_BUDGET_MAX_ENTRIES`; при исчерпании реестра запросы получают ту же
  ошибку перегрузки, а не неограниченный рост памяти.

### 8. Несколько процессов

Сохраняется решение ADR-0019: **единственный владелец** исходящего трафика —
процесс worker/Gateway. Общий межпроцессный механизм не вводится.

`AMOCRM_BUDGET_REPLICAS` должен равняться **1**. Значение больше одного
отклоняется при загрузке конфигурации и создании limiter. Простое деление
ставок на N не разделяет начальные запасы и не гарантирует общий лимит.
Поддержка нескольких владельцев требует общего координатора и отдельных
тестов отказов, перезапуска и смены владельца; статический раздел больше
не поддерживается.

Процесс не обнаруживает другие процессы автоматически: оператор должен
обеспечить единственного владельца исходящего трафика. Быстрые перезапуски
также не сохраняют историю допусков.

CLI `cmd/integrations` — отдельный короткоживущий процесс с собственным
limiter на тех же ставках. Он выполняет единицы запросов на команду оператора
и остаётся отдельным исключением: его трафик не координируется с worker,
поэтому общий потолок между CLI и worker не гарантирован.

## Наблюдаемость

| Метрика | Метки | Смысл |
| --- | --- | --- |
| `amocrm_budget_wait_seconds` | `outcome`: `admitted`, `canceled`, `deadline_exceeded`, `overloaded` | время ожидания разрешения |
| `amocrm_budget_waiting` | нет | текущее число ожидающих вызовов |
| `amocrm_budget_rejected_total` | `scope`: `pair`, `account`, `process`, `wait`, `registry` | отказы из-за заполненной очереди |
| `amocrm_budget_throttled_total` | `scope`: `pair`, `account` | какой бюджет задержал допуск |
| `amocrm_requests_total` | `outcome`, включая `429` | фактические запросы и ответы amoCRM |

`account_id` и `integration_id` в метки не попадают. Диагностика конкретного
аккаунта — по структурным логам с идентификатором запроса.

## Внешние приложения

Limiter учитывает только наш трафик. PHP и сторонние интеграции аккаунта
расходуют тот же бюджет amoCRM, поэтому `429` остаётся возможным и
обрабатывается с учётом `Retry-After` (см. ADR-0019).

## Последствия

- Аккаунты больше не мешают друг другу; изоляция покрыта тестами.
- Допуски ограничены текущими bucket'ами даже при задержках таймеров.
- При постоянной перегрузке часть работы отбрасывается с классифицированной
  ошибкой вместо неограниченного роста очереди; фоновые задачи повторяются
  через механизм задач.
- Горизонтальное масштабирование Gateway требует общего координатора бюджетов.
