# ADR-0039: Интеграции amoCRM и единственный владелец OAuth при переносе виджетов

Статус: **Proposed — готово к review ПВ-01**. Дата: 2026-10-22.

Задача: ПВ-01.01. Решение задаёт требования к реализации ПВ-02/ПВ-03;
оно не подтверждает готовность моста, импортера или переключение клиентов.

## Контекст и подтверждённое поведение

Core уже разделяет `integrations` и `installations`: `client_id` уникален для
интеграции, установка уникальна по `(integration_id, account_id)`.
См. [схему](../../migrations/000001_init.up.sql),
[границы capabilities](0008-multi-widget-capability-boundary.md) и
[OAuth service](../../internal/oauth/service.go).
Текущий callback требует сохранённый одноразовый `state`, проверяет аккаунт
через amoCRM и вызывает `SaveInstallation`. Этот метод активирует установку,
заменяет credentials и ставит `webhook.reconcile` —
[реализация](../../internal/oauth/store.go). Его нельзя использовать как
неявный импорт с немедленным запуском продукта до завершения миграции.

В SSD публичный код продукта может отличаться от OAuth-приложения:
`oauth_widget_code`, суффикс `_private` и aliases разрешаются в
[AmoOAuthResolver](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Services/AmoService/AmoOAuthResolver.php).
[AmoServiceBase](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Services/AmoService/AmoServiceBase.php)
загружает приложение и токен, устанавливает SDK callback обновления токена;
уже созданный клиент держит credentials в памяти.
[AmoAuthController](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Http/Controllers/AmoAuthController.php)
принимает callback и самостоятельно записывает токены через `storeAccessToken`.
Остановка cron или удаление записи из кэша не останавливают эти пути.

Официальная документация amoCRM, проверенная 22.10.2026:

- Refresh token одноразовый; при обмене нужно сохранить новую пару. В запросе
  обмена `redirect_uri` должен совпадать с настройкой интеграции.
  [Пошаговый OAuth](https://www.amocrm.ru/developers/content/oauth/step-by-step).
- Установка связывает интеграцию и аккаунт. У одной такой связи могут быть
  несколько пар токенов, выданных разным администраторам.
  [Модель OAuth](https://www.amocrm.ru/developers/content/oauth/oauth).
- Установка публичного виджета вызывает callback с `code`, `referer`,
  `from_widget`. Такой вход отличается от начатого нами OAuth со `state`.
  [Авторизация публичных интеграций](https://www.amocrm.ru/developers/content/oauth/auth-public-integrations).

Следовательно, единственный владелец обновления — наше архитектурное
ограничение, а не утверждение, что amoCRM физически допускает только одну
пару токенов. Наличие второй пары не разрешает двум платформам независимо
исполнять один продукт.

## Решение по интеграциям

**Для существующих продуктов сохраняем существующую интеграцию/client_id
по умолчанию.** Перенос сервера сам по себе не требует создания нового
продукта в amoMarket. Пригодность конкретной интеграции подтверждается
инвентаризацией и пилотом, а не предполагается для всех 13 виджетов.

Сохраняем действующий Redirect URI на первом переходе через совместимый
приёмник по прежнему адресу. Перенос адреса в настройках интеграции — отдельная
операция после проверки обмена/refresh и публичной установки. Документация
не является доказательством, что любая смена URI или импорт любой старой пары
пройдёт без повторной авторизации.

Новая интеграция нужна как явное исключение, если нет контроля над прежними
настройками/секретом, прежняя identity не соответствует новому продукту либо
правила публикации требуют отдельную интеграцию. Для исключения фиксируются
новый `client_id`, повторное согласие администратора, обновление виджета и
сохранённых автоматизаций, сопоставление коммерческой истории и условия
отключения старой интеграции. Токен старого `client_id` не переносится в новую
интеграцию. При неподтверждённой совместимости пилот этого продукта не запускается.

**Новое Распределение — отдельный новый продукт сразу в Core.** Его OAuth,
установка, lifecycle и исполнение принадлежат Core с первой установки.
В SSD создаётся только связанная проекция для обёртки оплаты и явно разрешённых
существующих endpoint. Проекция не содержит amoCRM refresh token и не включает
старую автоматизацию. РС-12 не является переносом старого Распределения из SSD.

## Две независимые области владения

| Область | Ключ и правило |
| --- | --- |
| Исполнение продукта | `amo_account_id + product_code`; отдельная функция только для явно разделённых частей Активности. Передача регулируется ADR-0040/ADR-0044 |
| OAuth credentials | `integration_id + amo_account_id`; ровно один runtime-владелец пары и её refresh. Нельзя делить refresh по функциям Активности |
| Сопоставление SSD | Явная связь `product_code ↔ public widget_code ↔ oauth_widget_code/client_id ↔ integration_id ↔ installation_id`, с account-specific overrides |

Код продукта не заменяет `integration_id`. `_private` не отбрасывается
произвольным преобразованием при импорте: сверяется реальный `client_id`.
Несколько продуктов могут использовать одну OAuth-установку. Тогда передача
credentials затрагивает **всех** потребителей этой установки в SSD, включая
служебную сверку аккаунта, callback, очереди и оставшиеся функции Активности.
Нельзя выбрать «первый пригодный токен аккаунта» как замену отсутствующей
авторизации конкретного продукта.

Реестр передачи содержит отдельные `credential_owner`, `credential_epoch`,
идентификатор операции и receipt остановки источника. Версия credentials,
lease refresh из ADR-0017 и `routing_epoch` продукта имеют разные назначения.
OAuth reauthorization не меняет владельца исполнения и не сбрасывает
монотонно возрастающий `routing_epoch`.

## Передача SSD → Core

1. **Prepare.** Инвентаризировать alias, интеграцию, установку, scopes,
   действующий URI, все readers/writers credentials и внешние подписки.
   Зарегистрировать интеграцию Core с правильной identity; подготовить
   установку без допуска продуктовых команд. Проверить типизированные операции
   для остающихся функций SSD. Секрет интеграции передаётся операторским каналом,
   а не через браузер или обычный endpoint оплаты.
2. **Fence и quiesce.** Durable-запрет в SSD закрывает начало refresh,
   использование локального SDK и запись OAuth callback для данной установки.
   Уже начатые refresh и обмены code должны завершить сохранение либо получить
   явно зафиксированный неизвестный исход. ACK источника включает последнее
   поколение credentials и отсутствие незавершённых writers. Удаление кэша,
   истечение TTL и недоступность SSD не считаются ACK. Если SDK нельзя надёжно
   оградить по установке, остановить и дренировать затронутые процессы целиком
   в обслуживаемом окне, сохраняя durable-запрет при рестарте.
3. **Stage.** Только после ACK экспортировать последнюю известную пару,
   срок действия и identity в отдельный защищённый одноразовый importer Core.
   Перешифровать средствами Core, привязать к installation и операции переноса;
   сохранить карантинное состояние без refresh, jobs и webhook reconcile.
   Импорт идемпотентен по операции/исходной версии. Не помещать токены в ClickUp,
   логи, аргументы CLI, обычные файлы отчётов или payload проекции SSD.
4. **Commit ownership.** Координатор фиксирует новый `credential_epoch`
   и владельца Core после подтверждения сохранённой пары. SSD остаётся
   ограждённым даже при потере ответа. Core допускает OAuth только при durable
   commit и совпадении поколения; неопределённость блокирует обе стороны.
   Это последовательный протокол с журналом восстановления, не обещание
   атомарной транзакции между двумя базами.
5. **Validate и resume.** Проверить account ID через amoCRM, разрешения,
   обычное чтение и управляемый refresh в Core; результат refresh сохранить
   по ADR-0017. Остальные функции SSD получают доступ через подготовленные
   операции Core. Продукт Core включается только после собственного quiesce
   ACK источника и фиксации нового routing epoch по ADR-0040/ADR-0044.
   OAuth готовность сама по себе продукт не активирует.
6. **Retire.** Удалить рабочие копии пары из SSD и его кэшей после сверки;
   оставить сведения о передаче без секретов. Запрет локального refresh
   сохраняется и после удаления: восстановление старой БД не должно вернуть
   SSD право на использование старого токена.

Если обнаружен неизвестный исход старого refresh, экспорт «последнего токена
из БД» запрещён: он мог уже быть израсходован. Нужна успешная поздняя
финализация исходного владельца или новая авторизация. Аналогично ведёт себя
Core: [ADR-0017](0017-oauth-refresh-lease.md) запрещает повтор после истечения
lease с неизвестным результатом. ПВ-03 должен обеспечить тот же инвариант
на стороне SSD; текущий SDK callback этого протокола не реализует.

## Callback, повторная авторизация и входящие события

Прежний callback URL остаётся совместимым ingress, но не вторым независимым
OAuth writer. До пилота оба обработчика должны проверять durable ownership
и поколение перед записью. Отложенный ответ прежнего callback после передачи
не может заменить новую пару или активировать установку.

Для потока со `state` маршрут и integration берутся из серверной записи
авторизации. Повторное использование state/code не допускается. Callback,
начатый до смены поколения, завершается по прежней операции либо требует
новой авторизации; его нельзя молча применить к новому поколению.

Для публичной установки без нашего `state` нужен отдельный проверенный
приёмник (работа РС-12/ПВ-03), а не отключение проверки state в текущем handler.
Integration выбирается по зарегистрированному входу и проверенному реестру;
`referer`, `client_id`, `account_id` из входного запроса сами по себе не дают
доверенной account identity. До HTTP обмен регистрируется в durable intake-журнале по integration с
текущим intake_generation и уникальным hash code. Это поколение захватывается
до обмена и не подменяется прочитанным после HTTP credential_epoch. Поскольку
account ещё неизвестен, передача credentials требует integration-level barrier:
новые неизвестные callback временно откладываются, все прежние unresolved
intake операции разрешаются/сохраняются до quiesce ACK. После проверки account
операция привязывается к его credential_epoch только при неизменном intake
поколении и отсутствии handoff. Поздняя пара прежнего intake поколения
остаётся в карантине для восстановления/новой авторизации, не пишет рабочие
credentials. Краткая остановка публичных callback всей интеграции является
явной ценой безопасной передачи одной ещё не распознаваемой установки.
Единственный обработчик обмена сохраняет
полученную пару в защищённом pending-состоянии, проверяет аккаунт через amoCRM
и только затем сопоставляет её с установленным владельцем credentials.
Запись в рабочее хранилище проходит проверку `credential_epoch` и блокировку
передачи. Pending-пара не выдаёт право исполнять продукт.

Если определить владельца до обмена невозможно, общий приёмник должен
координировать обмен и передачу результата, исключая параллельный вызов старого
и нового обработчика. Для пары, ещё принадлежащей SSD, сохранение выполняет
ограждённый SSD writer; после передачи — Core writer. Этот путь должен быть
готов до изменения callback маршрута всей интеграции, иначе переключение
затронет ещё не перенесённых клиентов. При неизвестном исходе обмена code
нельзя повторять его вслепую; нужна сохранённая pending-пара или новая
авторизация. На первом пилоте допустима управляемая повторная авторизация,
если прозрачный публичный callback ещё не доказан; это фиксируется заранее
как клиентский сценарий, а не объявляется бесшовным импортом.

Обычные CRM webhooks, uninstall и события установки имеют отдельные маршруты.
Прежние адреса принимают запросы в совместимом ingress, который определяет
установку по доверенной серверной привязке и направляет событие текущему
владельцу продукта с routing epoch. Старый процесс не выполняет действие
напрямую. Во время quiesce события надёжно буферизуются/учитываются по
ADR-0044. Нельзя использовать account ID из payload как единственное
подтверждение продукта.

Реестр webhook destinations Core из [ADR-0018](0018-installation-lifecycle.md)
не даёт права удалить все подписки аккаунта. Принимаются только подтверждённые
старые destinations; неизвестные или принадлежащие соседнему продукту
не снимаются. Передачу OAuth нельзя автоматически связывать с немедленным
`webhook.reconcile`, удалением прежнего адреса или включением обработчиков.

## Доступ остающихся функций SSD

Core не раздаёт refresh/access tokens обратно в SSD. Остающаяся функция
вызывает именованную операцию с фиксированной схемой, например получение
данных аккаунта или чтение нужного типа CRM-событий. На стороне Core операция
связана с установкой, capability, аккаунтом, конкретной функцией и актуальным
владельцем исполнения; у мутаций есть operation ID и собственный контракт
неизвестного исхода. Клиент SSD аутентифицируется как служба, а не выдаёт
произвольный account ID за авторизацию. Применяются существующие tenant/live
policy guards и общий исходящий бюджет аккаунта.

Не вводятся методы `proxy(method, url, body)` или универсальная передача
произвольного CRM HTTP. Если нужной операции ещё нет, её реализуют и проверяют
до передачи credentials либо оставляют всю OAuth-установку в SSD. Разделение
Активности по функциям не является исключением из этого условия.

## Сбои и возврат

| Ситуация | Разрешённое действие |
| --- | --- |
| Сбой до ACK или неизвестный refresh в SSD | Core не использует staging; исходный refresh завершается либо запрашивается reauthorization |
| ACK есть, пара сохранена, commit не подтверждён | Обе стороны закрыты; восстановить состояние по журналу операции, не выбирать владельца по таймауту |
| Передача отменена до commit, Core гарантированно не использовал пару | Отменить staging, записать терминальный исход и новое поколение, затем явно разрешить SSD; поздний commit прежней операции запрещён |
| Core уже получил право или мог отправить refresh | Не восстанавливать старую пару SSD из резервной копии. Сначала установить состояние Core/claim; неизвестность требует восстановления или новой авторизации |
| Продукт возвращается в SSD после commit OAuth | Credentials остаются в Core; SSD продолжает через типизированные операции. Routing epoch увеличивается, credential owner не меняется |
| Нужен возврат именно OAuth в SSD | Отдельная симметричная операция с остановкой Core writers, ACK, последней парой и новым credential epoch; это не автоматическая часть отката продукта |

Недоступность Core после передачи означает временную недоступность зависящих
от него CRM-операций SSD. Автоматический fallback на старый токен запрещён.
Оплата через SSD имеет собственную политику доступности и не отменяет OAuth
или lifecycle запреты.

## Условия допуска первого пилота

1. Для выбранных аккаунтов составлена проверенная карта product/public/private
   кодов, client_id, scopes, callback URI, установок и всех потребителей OAuth.
2. Подтверждён сценарий сохранённой интеграции либо явно выбран новый client_id
   с reauthorization. Управление интеграцией и требуемые условия публикации
   проверены фактически; секреты доступны только разрешённым runtime.
3. Реализованы durable fence, остановка refresh/callback writers, ACK,
   одноразовый importer, карантин до commit и восстановление незаконченной
   передачи. Публичный callback проверен отдельно от state-based flow.
4. Проверены новая установка, повторная авторизация, поздний callback,
   потеря связи во время handoff, неизвестный refresh и restart старого SSD
   worker. Ни один из сценариев не допускает двух refresh-владельцев.
5. Остающиеся функции SSD работают через проверенные операции Core; возврат
   продукта в SSD не требует возврата токена. Чужие webhook destinations
   сохраняются, старые вкладки и адреса проходят маршрут совместимости.

ПВ-01 фиксирует эти решения и критерии. Реализация и доказательства перечисленных
условий относятся к ПВ-02/ПВ-03 и приёмке пилота; боевые настройки и токены
для подготовки этого ADR не читались и не изменялись.
