# ADR-0041: зеркало установок Core в SSD

Статус: Proposed — готово к review ПВ-01, не реализовано. Дата: 22.10.2026.
Задача: ПВ-01.03. Связанные решения: [OAuth](0039-widget-migration-oauth-ownership.md),
[владелец исполнения](0040-product-routing-ownership.md),
[оплата](0042-core-ssd-billing-adapter.md), [защищённый HTTP](0033-distribution-signed-http-connection.md).

## Решение

Core владеет установкой нового продукта, OAuth и его исполнением. SSD остаётся
действующей платформой и временным источником коммерческого расчёта. Новое
Распределение не мигрирует из SSD: связанная запись там нужна для оплаты и
ограниченного набора операций. Наличие зеркала само по себе не разрешает SSD запускать продукт,
обновлять его OAuth или обходить владельца исполнения. У нового продукта
исполнитель сразу Core. При подготовке миграции зеркало может существовать, пока
реестр маршрутизации ещё указывает SSD; только протокол ADR-0040 меняет владельца.

Стабильный коммерческий ключ — `(amo_account_id, canonical_product_code)`.
Core installation ID, OAuth integration ID, браузерный alias и поколение установки
не являются новыми коммерческими клиентами. Новый `installation_generation`
выдаётся Core при подтверждённой новой установке после uninstall; прежняя
коммерческая история сохраняется. Refresh, повторный callback и восстановление
OAuth действующей установки не меняют installation_generation. Дубликат
события переустановки возвращает то же поколение, а не выдаёт следующее.
Core хранит mapping ключа на SSD Account/AccountWidget ID; SSD хранит обратный
mapping и признак `installation_source=core`. У существующих записей сохраняются
первичный ключ, `paid_to`, история, партнёр и ранее выданный trial.

Реестр продуктов явно сопоставляет Core product, публичные aliases и SSD
`widget_code`. Уже существующий [AmoOAuthResolver](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Services/AmoService/AmoOAuthResolver.php)
мапит aliases и суффикс `_private` в публичный код для оплаты. Мост принимает только
зарегистрированные соответствия; произвольное удаление суффикса не создаёт новый
продукт. Неизвестный код — ошибка конфигурации, а не бесплатный продукт.
Новое Распределение имеет отдельный canonical_product_code и mapping; код
legacy Распределения не переиспользуется автоматически. Наличие старой покупки
не копирует её права в новый продукт без явной политики подписки.

## Почему обычный install не подходит

[POST /api/widget/install](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/routes/api.php) вызывает
[InstallWidgetAction](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Actions/Account/InstallWidgetAction.php):
обновляет аккаунт и установку, назначает trial **при отсутствующем `paid_to`**, пишет
историю, создаёт/обновляет контакт и при выполнении условий ставит сделку в очередь.
Даже отдельный `AccountWidget::updateOrCreate` вызывает [model hooks](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Models/AccountWidget.php)
поиска партнёра, создания аккаунта и изменения статуса клиента; обновление срока
вызывает [DealQueueAccountWidgetObserver](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Observers/DealQueueAccountWidgetObserver.php).
Поэтому техническая синхронизация не вызывает public install и не переиспользует
его массовые записи без выделения явных эффектов.

Legacy `install_state` выводится из локального OAuth и имени установщика. Зеркало
без токена сейчас может выглядеть как `access_lost`/`not_installed`. Требуется
отдельное отображение источника установки, фактического владельца исполнения
(включая «подготовка переноса») и состояния синхронизации, а также сведений об
авторизации Core. Нельзя подделывать локальный токен или `oauth_connected`, чтобы
исправить интерфейс. SSD OAuth cron и исполнители обязаны исключать зеркало по
владельцу, а административное отключение должно отправлять команду Core, а не
молча изменять лишь копию.

## Три сценария и коммерческие эффекты

| Сценарий | Техническое действие | Коммерческое действие |
| --- | --- | --- |
| `migrate_existing` | Связать проверенную существующую запись; сверить данные и владельца | Сохранить срок, trial, партнёра и историю; не создавать новую продажу |
| `first_install` | Создать mapping и минимальную запись нового клиента/продукта | Для перенесённого продукта — явный идемпотентный intent с прежней политикой SSD; для нового продукта — отдельная политика НП-01 |
| `reinstall` | Новое поколение в прежнем коммерческом ключе | Сохранить историю; повторный trial не возникает автоматически |

Обработчик `MirrorCoreInstallation` должен явно перечислять записываемые поля и
разрешённые эффекты. Подавление всех observers глобально недопустимо; локальный
путь записи заменяет нужные инварианты и аудит явными вызовами в транзакции.
Для `migrate_existing` отсутствие записи возвращает конфликт и требует сверки,
вместо автоматического превращения миграции в новую установку.

Коммерческие действия выполняются отдельной командой с `commercial_intent_id`,
`policy_version` и уникальностью эффекта по коммерческому ключу и типу права.
Для **первой установки перенесённого продукта** исходная политика сохраняет
поведение SSD: платному продукту `testing_period_day` либо 14 дней, бесплатному
назначение срока +10 лет, поиск/привязку партнёра и промокода, контакт, историю и
CRM-сделку при прежних условиях. Бесплатный срок — существующий способ учёта,
не новый тариф. Условия сделки берутся из
[DetectInstallLeadKindAction](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Actions/Account/DetectInstallLeadKindAction.php)
и [RakursCrmInstallLeadRouter](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Services/RakursCrm/RakursCrmInstallLeadRouter.php),
а партнёр — из правил model hooks, не из произвольного browser partner ID.
Это явные шаги commercial intent, а не повторный вызов legacy install.
До cutover продукта его версия политики и нужные onboarding-поля обязательны;
отсутствующая политика — ошибка readiness, а не незаметная потеря trial/сделки.
Техническая запись и durable намерение запуска коммерческого onboarding
согласуются через outbox; завершение каждого эффекта фиксируется отдельно.
Если техническое зеркало уже создано, первая коммерческая установка определяется
журналом намерений/историей, не существованием строки AccountWidget. Неизвестные
данные для партнёра/контакта оставляют соответствующий шаг pending, не считаются
успешно обработанными. Миграция старой строки не создаёт first-install intent.
Новый transport event или поколение не разрешает повторный trial. Внешняя сделка
исполняется через durable outbox с проверкой результата; статус `unknown` не
повторяется автоматически, пока нет доказательства безопасного повтора.
НП-01 определяет модель подписки Распределения; этот ADR не выбирает тарифы и не
включает скрытый trial. До решения допускается техническое зеркало с оплатой
`pending`, без доступа к коммерчески закрытым функциям.

## Новый узкий HTTP-контракт

Все пути ниже **предлагаются к реализации** и сейчас не являются существующим API.
Core вызывает SSD только сервером; browser widget JWT заканчивается на Core.

| Метод и путь SSD | Назначение и scope |
| --- | --- |
| `POST /internal/v1/core/installations/events` | `installation:sync`; применить полный снимок одной установки |
| `GET /internal/v1/core/installations/{account}/{product}` | `installation:read`; вернуть mapping, состояние, версии и hash |
| `POST /internal/v1/core/installations/reconcile` | `installation:reconcile`; сравнить до 100 явно разрешённых ключей; без автоматической коммерческой записи |

Платёжные чтения и обратная доставка invalidation определены в ADR-0042. Generic
proxy URL, произвольный метод SSD, SQL-поля или название PHP action в запросе
отсутствуют. Legacy `/api/widget/account/update` не входит в allowlist: его
[WidgetAccountUpdateAction](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Actions/Account/WidgetAccountUpdateAction.php)
обновляет пользователей/установленные виджеты и запускает market sync. CRM-справочники,
Telegram и Google получают самостоятельные контракты в своих этапах.

Обязательный envelope события (business `payload_hash` считается по
каноническому payload без самого hash; HMAC отдельно покрывает точные body bytes):

- `schema_version=1`, UUID `event_id`, `payload_hash`, `state_hash`, `occurred_at`;
- положительный `amo_account_id`, зарегистрированный `product_code`, Core
  `installation_id`, `installation_generation`, `state_version`;
- `scenario`, `lifecycle_state` (`active`, `disabled`, `uninstalled`),
  `authorization_state` (`connected`, `revoked`, `unknown`),
  `installation_source=core`, `function_routes[]` с function_code, owner, phase,
  routing_epoch и revision из ADR-0040 (mirror event не меняет владельца);
  обычный продукт имеет одну запись whole, Activity — observation/employee_work;
  сводное отображение mixed в UI не является третьим владельцем исполнения;
- минимальные `account_snapshot` (`subdomain`, отображаемое имя; для расчёта
  по пользователям — проверенное количество), отдельные account_metadata_revision
  и account_metadata_hash от единственного Core writer метаданных аккаунта, и
  `policy_version`; неизвестные обязательные коммерческие данные не заменять нулями.

state_hash покрывает только каноническое состояние продукта/установки и
function_routes, без event_id, occurred_at и транспортных полей. payload_hash
покрывает envelope конкретного события. Повтор той же state_version в новом
reconcile event допустим при равном state_hash. Метаданные аккаунта имеют
собственную revision/hash и не разрешают конфликт product state.

Для первой установки account snapshot обязателен; для последующих полей действует
явная схема «значение/неизвестно», а не очистка данных отсутствующим JSON-полем.
Контакт, промокод и согласие на звонок передаются только отдельным разрешённым
коммерческим intent. Не передаются OAuth access/refresh token, client secret,
пользовательский JWT, баланс или назначенный Core срок оплаты. Domain аккаунта
является метаданными; идентификация всегда по проверенному amo account ID.

Подписанный HTTPS повторяет **принципы**, а не credentials ADR-0033: отдельные ключи
Core→SSD и SSD→Core, key ID, HMAC-SHA256 по method, точному URI/query, account,
product, generation, timestamp, nonce и SHA256 точных body bytes. Разрешения ключа
ограничены direction/scope/product, grant связывает account и установку; сверяются
подписанные значения и body/path. Для bootstrap разрешён только provision scope
у доверенного Core, который уже проверил установку аккаунта. Допуск времени ±60 с,
nonce durable между репликами минимум 5 минут, новый nonce при повторе того же
business event. Ключи не попадают в браузер; HTTPS и trust reverse proxy проверяются
при развёртывании. Ротация и отзыв ключа независимы от пользовательского OAuth.

Ответ `200` содержит `event_id`, `applied|duplicate|superseded`, mapping, принятые
версии и hash. ACK допустим только после commit inbox + mapping + изменения
зеркала + необходимых outbox. При неизвестном результате отправитель повторяет
тот же event с новым nonce и получает сохранённый outcome. HTTP-коды:
`400` повреждённая схема; `401` подпись/nonce; `403` scope/grant;
`409` повтор ID с другим hash, конфликт mapping или сценария;
`422` неизвестный продукт/политика; `429` ограничение с Retry-After;
`503` временная недоступность. Ошибка не возвращается как legacy HTTP 200/205.

## Порядок, восстановление и удаление

Core фиксирует lifecycle update, изменения route owner/phase/epoch и зеркального
состояния с новой state_version и outbox в той же транзакции. Переключение без
переустановки тоже обновляет проекцию. SSD inbox имеет unique event_id; порядок
блокировок фиксирован: account, затем коммерческий product key. Метаданные
аккаунта сравниваются отдельно по account_metadata_revision: устаревший снимок
продукта A не перезаписывает более новые данные от B. При одинаковой metadata
revision и разном hash — конфликт. Принимаемое изменение billable account fields
одновременно повышает billing_revision и пишет outbox ADR-0042. Устаревшая
metadata часть игнорируется независимо от применимости product snapshot. Core назначает
`state_version` монотонно по этому ключу **сквозь все поколения**, а generation
также возрастает. Timestamp используется для диагностики, не для разрешения гонок.
Полный snapshot большей версии может применяться без пропущенных промежуточных
состояний; побочные коммерческие команды имеют отдельный журнал и такой пропуск
не разрешают. Меньшая версия/поколение — `superseded`, равная state_version с другим state_hash —
конфликт. Старый `uninstalled` не отменяет новую установку.

Удаление сохраняет tombstone и mapping; оно не удаляет платежи и не отменяет оплату.
Оно немедленно закрывает исполнение в Core. Недоступность SSD оставляет mirror sync
в `pending/retrying`; она не превращает установку в legacy install. Reconcile
сравнивает поколения, версии, hash и ID с последним authoritative Core snapshot,
чинит техническую копию через тот же inbox и не создаёт коммерческие эффекты.
Предложение для ПВ-03: доставка с backoff/jitter до 5 минут, тревога после 15 минут,
периодическая сверка каждые 15 минут пилота и полная суточная сверка. Это инженерные
начальные значения для review, не обещание доступности.

## Проверки реализации и передача в ПВ-03

1. Миграция сохраняет AccountWidget ID, срок, партнёра и историю; повторный event
   не меняет их и не создаёт сделку, trial или запись OAuth.
2. Первая установка перенесённого продукта сохраняет платный trial 14 дней /
   testing_period_day, бесплатный срок, партнёра, контакт и условную CRM-сделку.
   Дубли событий, timeout, заранее созданное зеркало и reinstall не повторяют
   эффекты. Новый продукт без политики НП-01 создаёт лишь зеркало с pending;
   перенесённый продукт без версии прежней политики не проходит readiness.
3. Переустановка сохраняет коммерческий ключ; поздний uninstall прежнего поколения
   и задержанный account snapshot не изменяют новую установку.
4. Crash после commit до ACK, потеря связи и дубли между репликами сходятся к
   одному mapping; подмена account/product/hash отклоняется.
5. SSD UI показывает Core ownership без локального токена; все legacy cron, jobs,
   вебхуки и ручные команды проверяют реестр владельца до исполнения.
6. OAuth revoke немедленно останавливает Core независимо от оплаченного срока;
   unpaid не удаляет OAuth. Reconcile после сбоя не восстанавливает отозванный доступ.

ПВ-03 реализует schema/mapping/inbox/outbox, выделение технических записей из model
hooks, UI зеркала, узкие authenticated endpoints и перечисленные проверки. ADR
не свидетельствует о готовности этих изменений или о проверенном production cutover.
