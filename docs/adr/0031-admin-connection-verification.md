# ADR-0031: наблюдения доступности amoCRM

Дата: 2026-09-19. Статус: принято.

## Контекст

`installations.status=active` описывает жизненный цикл установки. Наличие
credentials не доказывает, что amoCRM принимает их сейчас. Ручные проверки
уже проходят через durable command/job/receipt.

## Решение

Храним безопасную проекцию `installation_checks` вместе с терминальной
квитанцией check. Версия credentials записывается из фактически использованного
токена, включая успешное обновление внутри проверки. Завершение блокирует
установку и credentials в порядке OAuth и сравнивает версию и состояние.
Поздний результат получает outcome `superseded` без обновления проекции.
Свежий OAuth немедленно скрывает прежнюю проекцию при чтении.

Свежесть определяется `connectioncheck.FreshFor`: 90 минут, включительно
на границе. API возвращает `fresh_for_seconds=5400`. Scheduler запускает
проверки в среднем раз в час с jitter ±20% (48–72 минуты); максимальный
настраиваемый интервал 72 минуты. Временные ошибки дают backoff до шести часов;
429 соблюдает `Retry-After` даже если он больше шести часов. Неуспешная попытка
не равна удалению установки. Только 401 или явный OAuth `invalid_grant`
могут переводить актуальные credentials в reauth.

Scheduler выключен по умолчанию, использует существующий command API внутри
процесса Worker. Admission общий для ручных и фоновых проверок: session
advisory locks PostgreSQL обеспечивают один запрос на установку, до двух на
интеграцию и настраиваемый глобальный предел. Успешная lock session отделяется
от pgxpool; ожидающие не удерживают соединения. Поэтому OAuth может получить
рабочее соединение даже при `DB_MAX_CONNS=1`. Scheduler тоже отделяет одну
session. Бюджет PostgreSQL равен сумме рабочих pool всех реплик плюс общий
лимит checks и одна scheduler session на работающую реплику. Все реплики
должны иметь одинаковый глобальный лимит.

Расписание seeding ограничено 100 новыми установками на tick. Оно устойчиво
к рестартам; один lock scheduler и stable idempotency key на временное окно
предотвращают дубли при нескольких репликах. Заблокированные/удалённые
установки и активные refresh leases пропускаются. Фоновые проверки не
восстанавливают отключённые установки.

## Отклонённые варианты

- Менять смысл `active` или автоматически считать его успехом проверки.
- Хранить ответ `/account`, OAuth values или upstream error body.
- Порог свежести 5 минут при проверках в среднем раз в час.
- Process-local semaphore: не ограничивает несколько реплик.
- Удерживать рабочий pool во время ожидания: блокирует OAuth и completion.

## Последствия

Добавляется миграция `000018_connection_checks`. Старые квитанции не
переносятся автоматически: у них нет достоверного version fence.
До первой новой проверки API честно показывает unknown. Ошибка источника
и проверка amoCRM остаются разными фактами. Публичный widget API не меняется.
Worker получает новый выключенный по умолчанию scheduler и общий бюджет
диагностических запросов. Ручные проверки работают при выключенном scheduler.
