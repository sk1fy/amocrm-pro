# ADR-0032: Владение распределением и границы доступа

Статус: предложено к рассмотрению в РС-01; не утверждено и не реализовано.
Дата: 2026-10-01.

## Контекст

Распределение планируется через `amocrm-pro` с интерфейсами TeamOS и
новым виджетом amoCRM. TeamOS `company` уже владеет группами и графиками;
Core — OAuth, admission, webhook inbox и техническими операциями.
Текущая симуляция TeamOS не назначает ответственного в amoCRM.

У Core один webhook router на семейство событий, а `leads:status` уже
используется `leadstatus`. Существующая Activity policy требует live admin
и не является проверкой доступа обычного пользователя к отдельной сделке.
Нельзя считать общий account ID доказательством связи компании и installation.

## Предлагаемое решение

1. TeamOS `company` владеет правилами, сотрудниками, графиками, расчётом
   доступности, бизнес-очередью и историей решений. Core владеет OAuth,
   technical inbox/outbox, receipt/effect и результатом вызова amoCRM.
2. Связь company/account/installation подтверждается обеими сторонами с
   явной revision и отзывом. Существующие TeamOS UUID, графики и membership
   сохраняются. Совпадение email или роль amoCRM не повышают роль TeamOS.
3. TeamOS UI работает через свой gateway. Виджет работает через Core с
   проверенным amoCRM actor и узкой делегацией; TeamOS заново проверяет
   собственную роль. Service principal автоматического распределителя
   отделён от пользовательского и ограничен binding/capability/действием.
4. Admin API использует внутренние API владельцев и свои viewer/operator/
   admin роли. Оператор занимается диагностикой и безопасным восстановлением;
   бизнес-правила остаются в TeamOS. Прямой доступ к чужой БД запрещён.
5. Обычный сотрудник видит разрешённые сведения после серверной
   `CanViewLead`: tenant, подтверждённый actor, section access и CRM resource
   rights. Неизвестная policy не разрешает доступ. Текущая admin-only
   Activity policy не готова для этого. Отдельный технический admin-only
   пилот возможен только по явному выбору и не заменяет employee view.
6. Одно нормализованное событие доставляется каждому подписанному модулю
   с независимым durable состоянием. Общий статус «обработано» не заменяет
   подтверждения каждого потребителя. Ingress отвечает после commit.
7. Межсервисные сообщения принимаются идемпотентно, используют scope и
   payload hash. Неизвестный результат PATCH сверяется. GET/PATCH гонка
   не объявляется устранённой; exactly-once внешнего эффекта не обещается.
8. Первая реализация расширяет существующие Core API/worker и TeamOS company
   узким bridge. Новые Redis/брокер/микросервис не вводятся автоматически.
   Требования ADR-0012 к изоляции данных и явным портам сохраняются.

Полные матрицы ownership, прав, сценарии отказа и ссылки на код:
[РС-01.2](../specs/lead-distribution-v1/02-architecture-and-access.md).

## Рассмотренные альтернативы

- Расчёт графиков и выбор получателя в Core дублируют домен TeamOS и создают
  двух владельцев бизнес-решения.
- Прямой API amoCRM из браузера или TeamOS распространяет секреты и создаёт
  дополнительного владельца OAuth/исходящего бюджета.
- Общие таблицы и транзакции backend нарушают существующие service boundaries.
- Доступ к любой сделке по токену интеграции не доказывает права пользователя.
- Новый отдельный сервис без собственного необходимого домена увеличивает
  эксплуатационный объём; возможность выделения должна сохраняться портами.

## Последствия и критерии проверки

Следующие этапы должны реализовать binding, контракты bridge, fanout,
делегацию нового продукта и собственные приёмочные тесты. Существующие
`lead-status` и Activity проходят регрессию. Требуются отрицательные тесты
подмены company/account/installation/job ID, отзыва capability, разных
ролей двух систем, неполного импорта и повторной доставки.

Документ не изменяет действующую Activity policy, открытые API, схему БД,
поведение worker или развёртывание. Закрытие проектной задачи не является
утверждением ADR или подтверждением установленного виджета.
