# ADR-0013: подробное чтение CRM Events и совместимость запросов

Статус: принято для этапа 2. Дата: 2026-09-08.

## Решение о сохранении данных

История остаётся в CRM Events. Добавлено ограниченное поле
`linked_talk_contact_id`, обнаруженное матрицей BASE-02. Оно проходит клиент,
Gateway, JSONB-owner, protobuf и HTTP; хранится как bigint в миграции владельца
`000003_event_details`. Ноль означает отсутствие известной ссылки и не выводится
в JSON. Нулевое поле не меняет прежнюю каноническую сериализацию/hash события.
Изменение ненулевого значения обновляет существующее событие, а не создаёт новое.

Полный HTTP-ответ/raw-object storage не добавляется. Восемь прежних полей и новый
contact ID покрывают текущий контракт. Произвольные верхнеуровневые поля, `_links`
и `_embedded` по-прежнему не обещаются как сохранённые. Названия сущностей через
Events `with` и примечания — следующая задача обогащения. Вложенные неизвестные
поля `value_before/value_after` сохраняются. Отсутствующий payload нормализуется
в `[]`; явный `null` сохраняется. Это не архив исходных байтов JSON.

Существующий максимум каждой стороны B/A — 32 768 байт, ответа amoCRM — 4 MiB,
прикладного ответа — 3 MiB, RPC frame — 4 MiB. Проверка B/A, ID события до 128
байт и неотрицательного contact ID теперь выполняется также у owner, поэтому
иной Gateway не обходит правила. Превышение/некорректная страница явно отклоняется
целиком, без записи части страницы и ложного продвижения coverage. Карантин и
пропуск ошибочных окон не вводятся: исправить источник/причину и повторить sync
по существующему протоколу. Лимиты не означают, что любые CRM-данные любого размера
будут приняты; ошибка видима и данные не обрезаются молча.

## Запросы и представления

Текущий `GET /api/v1/widget/activity/panel` остаётся основным списком. К прежним
параметрам добавлены:

| Параметр | Семантика |
| --- | --- |
| `types` | До 32 различных точных типов, CSV |
| `type_prefix` | Буквальный префикс до 64 байт, например `task_`; `_` не SQL wildcard |
| `entity_type` / `entity_ids` | Один тип и до 100 положительных разных ID; IDs требуют type |
| `order` | `asc` по умолчанию или `desc`; пара `(created_at,event_id)` |
| `compact` | По умолчанию false; true не читает B/A из SQL и возвращает их как null |

Точные types и prefix объединяются через OR; период, авторы и сущности — через
AND. Сводка использует ту же фильтрацию на всём периоде. Группы Activity ещё не
вводятся: prefix — форма запроса, а не продуктовая классификация «звонки/задачи».
Идентификаторы фильтров ограничены ASCII буквами, цифрами и символами `_`, `-`, `.`, `:`.
Максимум точного type — 128 байт,
entity_type — 64; это не закрытый enum допустимых событий.

Для compact ответа обязательно `data.payloads_omitted=true`. Null в такой
проекции не означает null в исходном событии. Полный ответ остаётся прежним;
превышение его бюджета возвращает resource_exhausted, можно уменьшить limit или
явно выбрать compact. Оптимизация не превращает исходную историю в урезанную.

`GET /api/v1/widget/activity/events/{eventID}` читает одно сохранённое событие
целиком. Новый `EventReader` — дополнительный прикладной порт, а не расширение
обязательного старого интерфейса CRMEvents. Core выдаёт существующий read grant,
owner проверяет live policy и scope. mTLS разрешает точный GetEvent Core/Activity,
не разрешая Activity Apply. Missing/foreign/уже удалённый ID дают одинаковый
not_found. Пауза сбора не закрывает историю; отзыв pilot/capability/installation
по-прежнему запрещает доступ. Внешнего HTTP-вызова для detail нет.

## Курсоры и смешанные версии

Курсор v2 содержит позицию и SHA-256 нормализованных фильтров вместе с
integration/installation, периодом, order и compact. Списки сортируются и
дедуплицируются для fingerprint, не меняя исходный запрос. Размер страницы можно
изменить. Курсор не является подписью авторизации; доступ всегда проверяет
policy, а SQL всегда содержит trusted scope.

Курсор без v2 либо от другого набора фильтров отклоняется с invalid_argument;
клиент начинает с первой страницы. Legacy cursors не интерпретируются по старым
непроверяемым правилам. Каждый Query имеет один PostgreSQL snapshot для status,
страницы и сводки; разные страницы не имеют общего snapshot. Поздняя вставка
позади позиции не обязана попасть на следующую страницу, удаление строки позиции
не ломает её использование. Для обновлённой истории начать чтение заново.
Snapshot-экспорт остаётся отдельной будущей задачей.

Новый owner возвращает `read_version=2`. При новых опциях или любом непустом курсоре Core bridge, Activity
и RPC clients требуют этот marker и согласованный `payloads_omitted`. Старый
получатель или промежуточный Activity, теряющий новые поля, приводит к unavailable,
а не к незаметно нефильтрованному результату. Старые запросы без новых опций
и без курсора допускают старый marker=0. Так rollback owner не превращает v2
cursor в старую позицию без проверки фильтров. Повреждённый URL query отклоняется
целиком, а не читается с молча отброшенными параметрами.
Отсутствующий detail RPC также даёт unavailable; нет
fallback на другой backend или неограниченную выборку.

## Выпуск и откат

1. Сделать резервную копию и проверить owner schema. Если 000002 ещё отсутствует,
   сначала выполнить её предусмотренные prechecks retention; не редактировать
   старые migrations и не сокращать историю молча.
2. Остановить/дренировать старые collectors при обновлении. Применить 000003
   владельцем CRM Events. Обновить Gateway, CRM Events, Activity и Core совместимо;
   все collectors должны получать новый контактный атрибут и применять одну схему.
3. Проверить legacy panel, новые фильтры/compact/detail и sync. Уже запомненный
   legacy cursor сбросить. Если изменение набора полей сделало начатый scan
   нестабильным, использовать существующую диагностику и явный sync; не пропускать
   окно ради успешного статуса.
4. Ранее потерянные contact ID не восстановятся от одной миграции: исторические
   строки имеют ноль, возможное восстановление — последующим доступным backfill.
5. Старый runtime может читать прежние колонки после 000003, но не понимает новую
   семантику. Не оставлять старые и новые collectors одновременно: старый Gateway
   не передаёт contact ID, а старый writer не обслуживает его обновления.
6. Предпочитать rollback приложения с сохранением расширенной схемы и учётом
   потерянных новых возможностей. Down 000003 удаляет contact ID без восстановления;
   удаление колонки — отдельная осознанная операция, а не автоматический откат.

Физическое размещение и общий исходящий бюджет не меняются. Реальная установка
ZIP и production deployment не входят в локальную проверку этого этапа.
