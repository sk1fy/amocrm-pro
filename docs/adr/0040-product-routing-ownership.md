# ADR-0040: владелец исполнения продукта при переходе SSD → Core

Дата: 2026-10-22. Статус: **Proposed — готово к review ПВ-01**.
Задача: [ПВ-01.02](https://app.clickup.com/t/1amkccgbvj0).
Это контракт для реализации ПВ-03, а не описание работающей таблицы или API.

## Контекст и границы

Core уже отделяет integration от installation и проверяет lifecycle/capability
при приёме и исполнении работы ([ADR-0008](0008-multi-widget-capability-boundary.md),
[ADR-0018](0018-installation-lifecycle.md)). Эти проверки не знают, продолжает
ли SSD обслуживать тот же продукт. В SSD есть одновременно HTTP-вызовы,
очереди и плановые исполнители; смена браузерного бандла не выключает их.

Подтверждения в коде:

- [Регистрация встроенного продукта](../../internal/services/leadstatus/module.go).
- [Core policy](../../internal/corepolicy/policy.go) и
  [операции Распределения](../../internal/distribution/operation_execution.go).
- [SSD CopyLead HTTP/DP/Salesbot](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/Modules/Widgets/CopyLead/Http/Controllers/Widget/rkrs_copylead/MainController.php),
  [job](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Jobs/Widget/CopyLeadJob.php),
  [cron](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/routes/console.php) и
  [запуск воркеров](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Jobs/CustomDispatch.php).

Новая публичная версия Распределения принадлежит новой платформе с первой
установки. Ей не требуется миграция старого распределителя. Внутри новой
платформы правила/очередь TeamOS остаются у TeamOS: значение owner=core ниже
означает платформу исполнения, а не перенос всех продуктовых данных в Core DB.
Учётная запись SSD для Billing не делает SSD владельцем исполнения.

Новое и legacy Распределение имеют разные canonical_product_code: новый код
не привязывается автоматически к коммерческой строке старого продукта. Их
сопоставление для льготы/подписки требует отдельной продуктовой политики.
Различие кодов не разрешает конкурирующие назначения одной сделки: readiness
нового продукта отдельно проверяет/требует исключить пересекающиеся правила
старого распределителя. Пока совместимость не подтверждена, live для
пересекающегося scope закрыт; автоматический перенос старых правил не выполняется.

## Решение: идентичность и хранилище

В Core DB добавить отдельный реестр product_routes. Логическая схема:

| Поле | Назначение |
| --- | --- |
| account_id, product_code, function_code | Уникальный ключ маршрута; function_code=whole по умолчанию |
| owner | ssd или core; последний подтверждённый владелец |
| phase | active, freezing, frozen, preparing, activating, blocked |
| routing_epoch | Монотонное поколение исполнения; увеличивается для каждого переключения/возврата |
| revision | CAS-версия записи; увеличивается при любом изменении состояния |
| owner_installation_id, installation_generation | Установка, уполномоченная исполнять продукт на Core; для SSD — явное соответствие legacy identity |
| transfer_id, source, target | Идентичность и направление текущего переключения |
| source_fence_receipt, target_prepare_receipt | Ссылки на сохранённые подтверждения сторон с hash и версией протокола |
| updated_at, actor, reason | Аудит; время не используется для разрешения конфликтов версий |

Product code — стабильный код из каталога, не произвольный app_name браузера,
не OAuth client_id и не название тарифа. Соответствия legacy/public/private
кодов фиксируются по [ADR-0039](0039-widget-migration-oauth-ownership.md).
Коммерческая пара account+product остаётся стабильной после переустановки;
installation_generation и routing_epoch решают разные задачи и не заменяют друг
друга. Несколько установок одного продукта не получают несколько writer'ов.

Для Activity допускаются только заранее зарегистрированные функции observation
и employee_work. Нельзя создавать произвольные function_code из запроса.
Для остальных продуктов действует whole. Каталог запрещает одновременно
активный whole и его дочерние функции. Разделение вводится до пилота с явной
миграцией реестра. Подписка может покрывать обе функции; это не два тарифа.

Реестр исполнения не хранит OAuth-токены, срок оплаты, правила TeamOS или
данные продукта. Владение credentials определяется отдельно в ADR-0039.

## Начальное заполнение и права

- Новая подтверждённая установка Core получает owner=core только при
  отсутствии конфликтующего маршрута и разрешённом onboarding продукта.
  Наличие зеркала SSD не является конфликтом.
- Существующие установки SSD регистрируются как owner=ssd из проверенного
  инвентаря. Неизвестная строка не означает owner=ssd или разрешённый доступ.
- Включение проверки выполняется по продукту/когорте после сверки инвентаря.
  До него старый runtime остаётся legacy-only и не может участвовать в
  переключении. Нельзя объявить все аккаунты защищёнными одним feature flag.
- Изменения маршрута — только аудируемые команды оператора с role/scope,
  Idempotency-Key и expected_revision. Повтор возвращает ту же operation;
  тот же ключ с другим payload даёт конфликт. Browser endpoint только читает.
- Любое включение target повторно проверяет актуальный installation lifecycle,
  generation, capability и binding. Оплата не разрешает отключённую установку.

## Состояния операции

| Переход | Обязательное условие | Новое исполнение |
| --- | --- | --- |
| active → freezing | CAS revision, transfer_id, следующий epoch | Source закрывает новые admission; target закрыт |
| freezing → frozen | Сохранённый source fence и полный quiesce receipt | Обе стороны закрыты |
| frozen → preparing | Зафиксирована граница данных/очереди и relay позднего ingress | Только импорт без эффектов |
| preparing → activating | Target prepare receipt и успешная сверка | Обе стороны закрыты до authoritative commit |
| activating → active | CAS owner/epoch, оба receipt, актуальные права | Только target после проверки commit |
| Любая незавершённая фаза → blocked | Неполные evidence, unknown effect, конфликт | Target закрыт; source fence сохраняется |
| blocked → сохранённая фаза | Восстановлен тот же transfer, проверены receipts | По правилам этой фазы |
| Отмена → active прежнего owner | Target ограждён, отсутствие его эффектов подтверждено, новый epoch | Source возобновляется только после commit отмены |

Отмена хранится как терминальное состояние transfer, а не пропадает из аудита.
После рестарта нельзя перескочить фазу по времени или одному health check.

## Передача исполнения: сохранённый запрет вместо доверия к TTL

Распределённой транзакции между Core и SSD нет. Применяется сохраняемая
операция переключения с безопасным состоянием, в котором ни одна сторона
не начинает новые действия. Недоступность приводит к паузе, а не к двум writer'ам.

1. Core под CAS создаёт transfer_id, резервирует следующий routing_epoch и
   переводит маршрут в freezing. Текущий owner остаётся source для диагностики.
   Новые команды маршрутизатора сохраняются как ожидающие переключения.
2. Source атомарно записывает локальный fence для scope и transfer_id в своей
   БД. Все admission и dispatch-пути обязаны читать этот fence. После commit
   нельзя допустить новую мутацию продукта, включая старую очередь и cron.
3. Уже допущенные операции сохраняются в реестре in-flight. До внешнего HTTP
   необходим durable dispatch intent. Fence и регистрация intent сериализуются
   одним локальным guard; простаивающий процесс не может отправить HTTP после
   проверки, незаметно для drain. Process TTL или возраст job не доказывает
   отсутствие незавершённого внешнего действия.
4. Source завершает/переносит явно перечисленную принятую работу. Неотправленные
   задания можно передать target с прежней operation identity; uncertain
   внешние действия блокируют переключение затронутого scope. Source выдаёт
   сохранённый quiesce receipt только после доказанной остановки исполнения.
5. Receipt содержит scope, transfer_id, предыдущий и новый epoch, fence revision,
   версии всех обслуживающих runtime, границу очереди/данных и сведения об
   отсутствии in-flight/uncertain. Частичный обход исполнителей не принимается.
   Если старые binaries не соблюдают guard, их останавливают и исключают из
   запуска; пока это не подтверждено, receipt невозможен.
6. Target импортирует финальные данные и operation ledger, но не исполняет их.
   Сверка и готовность фиксируются отдельным prepare receipt. Core сохраняет
   оба receipt и коммитит owner=target, phase=active, новый epoch под CAS.
   Target начинает работу только после получения этого commit, а не по одному
   prepare. Source остаётся fenced даже при потере финального ответа.

Кэш с owner=ssd может быть старым в момент переключения. Поэтому кэш никогда
не отменяет локальный fence. Target не активируется без source ACK: если ACK
потерялся, Core запрашивает сохранённый результат той же операции, не считает
таймаут успешной остановкой и не выдаёт новый transfer поверх неизвестного.

Отмена до активации target тоже является управляемым переходом: target
подтверждает отсутствие исполнения/сохраняет fence, source получает новый
монотонный epoch. Запрет нельзя удалить вручную или сбросить откатом БД.
Возврат после активации — полноценное обратное переключение по
[ADR-0044](0044-product-cutover-and-rollback.md), без повторного использования epoch.

## Читатели и точки проверки

| Читатель | Проверка и поведение |
| --- | --- |
| Общий загрузчик | Проверенный amoCRM actor/account/product, route snapshot; выбирает UI, не предоставляет право исполнения |
| Core widget API и DP/Salesbot ingress | Scope из проверенного principal/секретного endpoint; route, lifecycle и capability до durable admission |
| Старый SSD HTTP endpoint | Тот же local fence до синхронной мутации; при owner=core — согласованный adapter/relay, не второй обработчик |
| SSD cron, daemon, очереди | Scope фильтруется до enqueue/claim и проверяется снова перед dispatch/записью |
| Core worker и product module | Epoch, generation, capability, актуальный lifecycle и продуктовая авторизация перед действием |
| TeamOS/админки | Показывают owner/phase/revision и pending transfer; работа с данными через API владельца |
| OAuth refresh | Собственный credential-owner guard ADR-0039; product route не является правом обновить токен |
| Billing/SSD mirror | Синхронизация учёта не меняет product route и не снимает fence |

Сохранённая job несёт scope, installation_generation, admission_epoch,
operation_id и семантическую идентичность исходного события. Несовпадение epoch
не разрешает просто перезапустить job с новым epoch: сначала определяется,
был ли эффект, и операция явно переносится либо завершается как superseded.
Ingress source остаётся ответственным за уже подтверждённые события после
финальной границы импорта: durable relay доставляет их в inbox target с
исходной identity и сохраняет до его durable ACK. До activation target лишь
принимает/дедуплицирует их; не исполняет. Протокол курсора и возврата relay
определён в ADR-0044. Source fence запрещает эффекты, но не этот служебный relay.

Служебные команды freeze/import/reconcile имеют отдельные права и не обходят
guard для произвольного продуктового исполнения.

Предлагаемые новые HTTP-операции (wire-схемы реализуются в ПВ-03):
GET /internal/v1/ssd/routes/{account_id}/{product_code}/{function_code},
операторские PrepareTransfer, ConfirmSourceQuiesced, ConfirmTargetPrepared,
ActivateTarget и AbortTransfer. Каждая изменяющая команда привязана к transfer_id
и expected_revision; transport — подписанный HTTPS с отдельными scope/ключами,
как у [моста](0041-core-ssd-installation-bridge.md). Нет SetOwner без протокола.

## Недоступность и старые клиенты

Стартовый review-default: route cache TTL 60 секунд. Свежий active-snapshot
разрешает лишь обратиться к исполнителю; локальный fence всё равно обязателен.
Просроченный snapshot для нового изменяющего действия требует refresh; если
Core недоступен — действие остаётся pending/получает retryable отказ. Read-only
UI может показать последний снимок с отметкой устаревания. Пустой ответ не
превращается в owner=ssd. Документированное недоступное состояние лучше
самовольного возобновления старой автоматизации.

Во время freeze ingress подтверждает доставку только после durable записи.
Если запись недоступна, он возвращает ошибку по контракту конкретного источника;
не обещается, что amoCRM обязательно повторит запрос. Нужен учёт coverage и
восстановление пропусков по продукту. После cutover старые URLs сохраняют
совместимый адаптер; допустимые rule_index/handler_name не меняются молча.

Старый JavaScript может вызывать amoCRM напрямую. Серверный route guard
не способен остановить такой код. До пилота инвентаризируют эти пути и либо
переносят мутации за проверяемый серверный admission, либо требуют проверенное
обновление/остановку старых клиентов. Одновременный запуск таких версий не
объявляется безопасным только потому, что новый загрузчик уже установлен.

## Приёмка реализации и альтернативы

Обязательны: одновременные transfer-команды; старый cache=ssd при активном Core;
потеря freeze/activate ACK; рестарт source после fence; живой старый binary;
отложенная job старого epoch; timeout внешней записи; uninstall/reinstall во
время transfer; попытка браузера выбрать owner; независимость соседнего аккаунта;
Activity observation в Core при employee_work в SSD; обратное переключение
без уменьшения epoch. Ни одна ошибка не должна активировать двух исполнителей.

Один глобальный owner по коду виджета исключает пилот по клиентам. Два кэша
без durable handshake допускают двойное исполнение. Одна длинная SQL-транзакция
не координирует две БД и внешний HTTP. Автоматическое переключение после TTL
не доказывает завершение внешнего запроса. Поэтому эти варианты отклонены.

Реализация требует расширить ПВ-03.01/.02: не только таблица и чтение, но
transfer state machine, локальные guards и receipts. Эти условия входят в
приёмку соответствующих задач; внедрение самого протокола вне ПВ-01.
