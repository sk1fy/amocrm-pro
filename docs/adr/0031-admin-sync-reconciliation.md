# ADR-0031: обновление sync-квитанций перед приёмом admin-команд

- **Status:** Accepted.
- **Date:** 2026-09-19.

Дополняет ADR-0027 и ADR-0028. Задача: AMO-1427.

## Контекст

Квитанция `activity-sync` обновлялась через bridge только при `Store.Get`.
Если после завершения CRM Events никто её не читал, сохранённый `pending`
продолжал блокировать любые новые команды над установкой.

## Решение

До открытия транзакции приёма `Store.Execute` выбирает pending/running
`activity-sync` только запрошенного объекта и обновляет их тем же путём,
что `Get`. Сначала закрывается результат SQL-выборки, затем вызывается
bridge. Все действия ограничены общим timeout команды. Новые внешние
вызовы выполняются без открытой транзакции и без advisory locks.

После обновления сохраняется существующая транзакция приёма:

1. `admin-key:*` сериализует запросы с одним ключом; сравнение хеша
   возвращает прежнюю квитанцию либо конфликт другого запроса.
2. `admin-target:*` сериализует приём по объекту.
3. `EXISTS` заново читает актуальные accepted/pending/running квитанции
   под lock. Уникальный частичный индекс остаётся дополнительной защитой.
4. Доменное изменение, новая квитанция и аудит коммитятся как прежде.

Обновление старой квитанции само по себе не разрешает команду. Если между
ним и транзакцией появился новый sync/check, `EXISTS` увидит его и вернёт
409. Возможен безопасный 409, если sync появился после предварительной
выборки; следующий запрос снова выполнит обновление. Конкурентные
обновления используют существующий условный UPDATE только незавершённых
квитанций: terminal-состояние не перезаписывается поздним running-ответом.

Running sync, неподтверждённый результат и недоступность bridge не
освобождают объект. Никакого timeout-based успеха или повторного sync нет.
Повтор Idempotency-Key возвращает прежний ID с актуализированным статусом;
новые команды и outbox-записи при повторе не создаются.

## Отклонённые варианты

- Вызов `refreshActivitySync` внутри транзакции busy-check: удерживает
  locks во время внешнего I/O и требует дополнительного соединения pool.
- Обязательный polling со стороны клиента: оставляет зависимость
  корректности Core от поведения CLI, админки и фоновых отправителей.
- Фоновый reconciler: отдельный lifecycle и задержка восстановления
  не нужны для исправления приёма следующей команды.

## Последствия

Команда установки с незавершённым sync дополнительно читает его статус
через существующий Activity bridge. При недоступном источнике объект
остаётся занят до подтверждения результата. HTTP-схемы, миграции,
публичный API, worker и семантика Activity не меняются.
