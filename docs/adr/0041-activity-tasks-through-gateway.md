# ADR 0041: Задачи панели Activity только через Gateway

Дата: 2026-10-28. Статус: принято (КА-01.08).

## Контекст

Вкладки новой панели ходили в amoCRM напрямую из браузера: очередь,
задача, сущности, справочники и завершение. Эти запросы шли мимо общего
лимитера Gateway (ADR-0019, ADR-0029), и несколько вкладок вызывали 429/403.

## Решение

Браузер обращается только к `/api/v1/widget/activity/tasks*` и
`/leads/{id}`. Сотрудник определяется из виджетного JWT; Core выдаёт
delegation с grant Gateway `own_tasks`, для завершения `complete_task`.
Activity проверяет настройки панели, а Gateway владеет доступом к amoCRM.

Gateway читает только задачи, где сотрудник — ответственный, и отклоняет
чужие строки. Это не расширяет видимость через права серверного токена.
Названия сущностей показываются только для сущностей из собственной
очереди: они берутся при загрузке очереди сразу после live-чтения задач
сотрудника и сохраняются в снимке. Отдача снимка, в том числе устаревшего,
не ищет карточки в amoCRM и в общем кэше названий; устаревший снимок
отдаётся без связанных меток. Сделку (название, воронку, статус, участников) сотрудник видит,
только если он её ответственный или у него сейчас есть открытая задача
на ней; это проверяется live в amoCRM, а не по снимку очереди, который
переживает переназначение задачи. Ошибка проверки доступа не даёт.
Вердикт кэшируется в памяти процесса по (установка, сотрудник, сделка)
не дольше TTL очереди (30 с). Иначе сделка возвращается как `restricted`,
а связанные метки для неё не строятся.

Очередь хранится в `activity_task_queues` (PostgreSQL): TTL 30 с, lease
20 с с fencing по токену, общая для вкладок и реплик. Ответ несёт
`fetched_at`, `fresh_until`, `complete`, `stale`. Во время отката
отдаются устаревшие данные с явной пометкой. Ошибки 429 используют
Retry-After, экспоненциальную задержку и jitter; ошибки авторизации и 403
блокируют повтор на 60 с.

Завершение одной задачи сериализуется между вкладками и репликами
lease-строкой `activity_task_completions` (45 с по часам PostgreSQL,
без advisory-блокировок на время HTTP). Под lease задача перечитывается:
уже завершённая возвращается без повторного PATCH. PATCH ограничен 25 с
вместе с перечитыванием. Если исход неизвестен (таймаут, 5xx, обрыв),
задача перечитывается: завершена — это успех, иначе очередь
инвалидируется. Ждущий запрос после короткого ожидания отдаёт
результат держателя или `unavailable` с Retry-After. Завершение во время
загрузки, включая первую, повышает версию очереди: такая загрузка
публикуется просроченной и отдаётся как `stale`.

## Отклонённые варианты

Redis для кэша противоречит ADR-0001. Кэш в памяти процесса не
объединяет загрузки реплик. Прямой режим браузера как запасной
возвращает исходную проблему с бюджетом.

## Последствия

Каждый запрос виджета по-прежнему проверяет сотрудника через
`users/{id}` в Core Policy (ADR-0011). Событийной инвалидации нет:
изменения в amoCRM видны по TTL. Кэши названий и типов задач живут
в памяти процесса Gateway. Снимки, записанные до появления названий,
показываются без названий до следующей загрузки.
