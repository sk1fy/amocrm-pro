# ADR-0043: общий исходящий бюджет amoCRM в период Core + SSD

Статус: Proposed — подготовлено к review ПВ-01.05; реализация и проверка на
нагрузке относятся к следующим этапам. Дата: 2026-10-22.

## Основания

[ADR-0029](0029-outbound-budget-account-scope.md) ограничивает Core по паре
account/integration и аккаунту, но прямо исключает координацию с PHP и CLI.
[limiter.go](../../internal/integration/amocrm/limiter.go) хранит состояние в
процессе. [DoJSON](../../internal/integration/amocrm/client.go) получает допуск
на каждой HTTP-попытке, включая повтор после refresh. Это полезная граница,
но два независимых limiter не образуют один бюджет.

В SSD [AmoServiceRateLimitHandler](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Services/AmoService/AmoServiceRateLimitHandler.php)
использует Redis sliding window по `widget_code/account` и по account. При
недоступности Redis он продолжает работу с локальной задержкой; retry после
429 не получает новый слот. Вложенная callback-обёртка подавляет повторное
списание, поэтому она сама по себе не доказывает учёт каждого HTTP-запроса.
Потребители включают [чтения](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Services/AmoService/AmoServiceGetData.php),
[поиск](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/app/Services/AmoService/AmoServiceGetDataSearch.php),
старое [Распределение](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/Modules/Widgets/LeadDistribution/Http/Controllers/WidgetRakursLeadDistributionController.php)
и служебные команды. Настройки расширенных лимитов находятся в
[config/amo.php](https://github.com/Filipp22/rakurs-ssd/blob/a3916751233f9a9389a264ff70909a5c555c0242/config/amo.php). Наличие этих настроек
не доказывает актуальность купленного пакета.

Официальная [документация amoCRM](https://www.amocrm.ru/developers/content/api/recommendations)
на дату проверки указывает 7 запросов/сек на интеграцию и до 50 на аккаунт;
превышение возвращает 429, повторные нарушения могут привести к блокировке
403. Увеличение лимитов возможно дополнительным пакетом. Следующие числа —
наши консервативные настройки пилота, а не новое описание лимитов amoCRM.

## Решение: один узкий координатор допуска, два разрешённых транспорта

Authoritative budget хранится в **существующем PostgreSQL Core**. Core
worker/Gateway предоставляет `Budget.TryAcquire`, SSD обращается к нему
через подписанный служебный HTTP-контракт. Внутренний Gateway вызывает ту же
прикладную реализацию через порт. Произвольных URL, payload amoCRM и токенов
в этом контракте нет. Это не HTTP-прокси и не новая платформа очередей.
SSD не получает DSN Core; продуктовые модули не получают порт бюджета,
поскольку обращаются к узким Gateway-операциям.

Сохраняется [ADR-0001](0001-postgresql-without-redis.md): Redis не становится
зависимостью Core. После реализации и общего rollout это решение заменяет
process-local authority раздела 8 ADR-0029 для подключённого трафика;
остальные правила ограниченности ожидания и typed errors сохраняются.
До rollout действует существующий код: документ не создаёт гарантию сам.

Владелец OAuth определяется отдельным решением ПВ-01.01. Для Core-owned
credentials исходящий HTTP выполняет только Gateway, включая запросы старых
функций через согласованные узкие порты. Для ещё SSD-owned credentials SSD
выполняет HTTP сам, предварительно получив общий допуск. Координатор не
обновляет и не передаёт токены. Один refresh owner и один budget authority
являются разными обязанностями.

### Идентификаторы и атомарное решение

- Ключ аккаунта — канонический amoCRM account ID; ключ пары — account ID и
  **OAuth client ID**, а не локальный UUID Core, код виджета или installation.
  Явная проверенная таблица связывает локальные идентификаторы с client ID.
  Неизвестная связь отклоняется; `unknown` не создаёт бесплатный новый bucket.
- Класс `foreground` — интерактивные запросы и рабочие автоматизации клиента;
  `background` — backfill, перенос данных, периодическая сверка и массовый
  импорт истории. Класс назначает серверный обработчик, а не браузер.
- Параметры запроса: scope, attempt ID, разрешённый класс, версия политики
  бюджета, deadline. Подпись покрывает method/path/body hash, timestamp,
  nonce и audience; разрешённые SSD identities и scope проверяются на сервере.
  Identity берётся из проверенной установки/служебного binding. Request body
  сам по себе не является доказательством account или владельца.
- Короткая транзакция блокирует account row, затем pair row в фиксированном
  порядке; проверяет общие next-admit timestamps, cooldown и, для фона,
  дополнительные timestamps фона. При допуске все применимые значения
  обновляются атомарно. `next = db_now + 1/rate`, burst = 1, будущие слоты
  не выдаются. При отказе бюджет не расходуется. Это предлагаемая реализация,
  а не требование использовать существующий in-memory календарь как есть.
- DB clock задаёт время учёта. Отрицательный скачок даёт консервативное
  ожидание; при обнаруженном скачке вперёд/несогласованном времени readiness
  закрывается до восстановления и процедуры drain. Согласованность часов и
  failover входят в эксплуатационную приёмку.
- Допуск одноразовый и действует максимум **100 мс от локального начала
  вызова TryAcquire**, измеренного monotonic clock отправителя. Ответ позднее
  этого срока отбрасывается. Непосредственно перед HTTP транспорт повторно
  проверяет срок; неиспользованный допуск не возвращается. Никаких запасов
  разрешений в процессе. Списание фиксируется до ответа координатора;
  потеря ответа может только уменьшить пропускную способность.
- Повтор сетевого запроса TryAcquire с тем же attempt ID не выдаёт второй
  permit: хранится короткая receipt с исходным сроком. Новый HTTP-attempt
  имеет новый ID и новый расход. Внешний operation ID при этом не меняется.
  Рекомендуемая retention receipt — 10 минут, не меньше срока подписанного
  запроса и nonce. Это не retention истории бизнес-операций.

Допуск и фактическая отправка разделены сетью/планировщиком. Срок 100 мс —
стартовый инженерный параметр, проверяемый метриками RTT/expired permits.
Реальный HTTP transport должен проверять срок как можно ближе к отправке;
задержка ОС после последней проверки всё ещё возможна. Поэтому ставки 6/40
и burst=1 дают запас, но здесь **не обещается строгий лимит фактических
пакетов у amoCRM**. Нельзя поднять ставки до 7/50 и сохранить прежний запас.
Сторонние интеграции также расходуют аккаунт независимо от координатора.

### Настройки пилота, подлежащие review

| Предел | Значение | Поведение |
| --- | --- | --- |
| Все запросы пары | 6 rps, burst 1 | Общий расход SSD + Core + CLI |
| Все запросы аккаунта | 40 rps, burst 1 | Запас для внешних интеграций; не гарантия отсутствия 429 |
| Фон пары / аккаунта | 1 / 5 rps, burst 1 | Расходует также оба общих бюджета |
| Приоритет рабочих запросов | Фон не допускается 2 с после последнего foreground demand | Долгий foreground может остановить миграцию; это допустимо |
| Ожидание foreground | До 2 с и не дольше deadline | Затем typed overload без HTTP |
| Ожидание background | Без парковки worker | `not_before` + jitter в durable job |
| Одновременно ожидающих | 64 на пару / 512 на аккаунт / 4096 на процесс | Предохранители клиентов; coordinator не держит waiters |
| DB transaction / lock wait | 50 / 20 мс | Ошибка даёт unavailable, без локального fallback |
| TTL permit | 100 мс от начала вызова | Истёкший допуск сгорает |

`foreground demand` обновляется даже при отказе и ограничивается по частоте
записи: один отказ не должен создавать бесконечную DB-очередь. TryAcquire не
является долгим blocking RPC. Отказ возвращает время следующей проверки;
повтор учитывает его, deadline и jitter. Rate limiter входа координатора,
ограниченный pool, метрики lock contention и очистка idle rows необходимы
до пилота. Удалять row можно только после прохождения всех next timestamps,
cooldown и периода безопасности; рестарт не обнуляет timestamps.

Переопределения — единая версионированная конфигурация координатора с
подтверждением пакета и проверкой запаса/TTL. SSD-local overrides не
повышают общий бюджет. По умолчанию ни один аккаунт автоматически не
наследует 100 rps из старого конфигурационного файла. Уменьшение бюджета
применяется без создания новых полных bucket; повышение требует review.

### 429, неизвестный результат и отказ координатора

Ответ 429 передаётся координатору как scoped feedback от разрешённого
транспорта. `Retry-After` (секунды либо HTTP-date) задаёт минимум паузы:
не обрезаем его до 60 с и не повторяем раньше. При отсутствии корректного
заголовка применяется backoff 1, 2, 4, … до 60 с плюс положительный jitter.
Cooldown консервативно ставится на аккаунт, потому что upstream не всегда
позволяет различить pair/account limit. При повторных 429 фоновая работа
приостанавливается, ставка аккаунта временно снижается вдвое; восстановление
только после 5 минут без 429, шагом не более 10% исходной ставки в минуту.
403 не лечится бесконечным retry: диагностика причины и остановка затронутых
операций. Параметры адаптации проверяются нагрузочными тестами.

**Разрешение повторить нагрузку не является разрешением повторить эффект.**
До HTTP overload/expired permit можно повторять безопасно. GET после
временной ошибки повторяется с новым допуском. Для POST/PATCH/удаления
retry разрешает прикладной контракт операции: явный отказ upstream,
идемпотентность или доказанная сверка. Timeout/потерянный ответ не доказывает
неисполнение; operation остаётся unknown/reconcile, а создание сделки или
отправка уведомления не запускаются заново из-за наличия свободного бюджета.
Каждая реальная повторная попытка, в том числе после refresh, расходует
допуск. Автоматические SDK retries и pagination требуют transport-level hook
в SSD; обёртка callback недостаточна. OAuth token endpoint получает отдельный
ограничитель своего владельца и не объявляется API v4 по этому ADR.

При недоступности координатора/DB оба транспорта прекращают новые HTTP
попытки; jobs сохраняются, пользователи получают временную ошибку. SSD
`usleep` fallback на подключённых scopes выключен. Уже отправленный запрос
дожидается результата в рамках deadline. Отказ не запускает второй transport,
не меняет OAuth owner и не выдаёт разрешение из устаревшего кэша.

### Rollout и проверяемый результат следующих этапов

1. Инвентаризировать весь HTTP: API, workers, cron, SDK pagination/retries,
   bootstrap, операторский CLI и обращения не из 13 продуктов. Для пилотного
   аккаунта учитывается весь Rakurs-трафик. CLI exception из ADR-0029 для
   подключённых аккаунтов прекращает действовать.
2. Реализовать coordinator и оба transport adapters с контрактными тестами;
   shadow mode только измеряет и не объявляется координацией. Bootstrap с
   неизвестным ID ограничивается отдельным малым бюджетом; до подтверждения
   mapping запрещена обычная работа. Canonical account charge выполняется
   после определения ID, как отдельная проверяемая ветка.
3. Остановить выдачу запросов подключаемых scopes со всех старых экземпляров,
   drain фактических in-flight запросов, выдержать 1.1 с после последнего
   подтверждённого отправления. Включить единый режим на SSD и Core; mixed
   versions без adapter не допускаются. Нельзя включить пилот только флагом
   одного сервиса. При неизвестном состоянии старого executor остановка
   подтверждается до открытия нового режима.
4. Проверить рестарт без потери бюджета, поздний permit, потерю ответа,
   недоступность coordinator, clock jump и PostgreSQL failover. После
   failover с возможной потерей commit остановить выдачу, погасить старый
   primary/его доступ и все старые permits, затем drain + окно 1.1 с;
   автоматическое продолжение с пустыми rows запрещено. Для пилота не
   обещается seamless failover при асинхронной репликации.
5. Нагрузочный сценарий: одновременные SSD + Core + CLI, несколько продуктов
   одного аккаунта и несколько аккаунтов; фон насыщает квоту, foreground
   продолжает получать допуски. Проверять реальные отправки, не только
   количество TryAcquire. Цель review: p95 TryAcquire <50 мс и отсутствие
   роста очереди DB на ожидаемом пилотном масштабе; это не уже измеренный SLO.
6. Rollback coordinator: остановка обоих транспортов и drain. Возврат двух
   независимых полноразмерных limiter не допустим; временно оставить только
   один согласованный отправитель либо сохранить общий координатор.

Метрики: admitted/denied/expired/cooldown по конечным class/caller/outcome,
latency и DB lock waits, доля 429, возраст отложенного фона. Tenant IDs —
только в защищённых структурных логах. Подтверждение безопасности смены
владельца исполнения не заменяется бюджетом: проверка owner/epoch и durable
quiesce остаются отдельными условиями ПВ-01.02/06.

## Альтернативы и последствия

- Статическое деление 7/50 между независимыми процессами не решает burst,
  рестарты и число SSD workers; отклонено.
- Существующий Redis SSD мог бы стать общим backend за тем же портом, но
  требует нового ADR с измерениями и отказами по ADR-0001. Для первого
  пилота выбираем PostgreSQL; импорт PHP Lua в Go не является готовой общей
  гарантией.
- Отправлять весь трафик через generic HTTP proxy отклонено: это расширяет
  доступ к credentials и действиям вместо узких Gateway ports.
- Цена выбранного решения — дополнительная DB-транзакция и служебный RTT
  для SSD. Если измерения не проходят целевые пределы, пилот не включается;
  изменение backend проектируется за тем же контрактом с отдельной проверкой.

ПВ-01 завершает проектирование. Реализацию общего допуска необходимо явно
включить в foundation/bridge до одновременного боевого исполнения Core+SSD;
существующие limiter остаются недостаточным доказательством этого условия.
