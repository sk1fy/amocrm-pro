# ADR-0012: Контракт отдельно размещаемого продуктового модуля

Статус: принято как обязательное правило дальнейшего расширения. Это не отчёт
о переносе на другой физический сервер и не реализация нового модуля.

Дата: 2026-09-08.

## Контекст

Activity и CRM Events уже имеют собственные логические БД, Repository-порты,
прикладные реализации, отдельные binaries и embedded/gRPC composition.
Потребность владельца — сохранить эту возможность при росте Activity и при
добавлении других продуктов. Перенос существующего модуля должен менять
развёртывание, а не бизнес-логику, публичный Core origin или код виджета.

Решение дополняет [ADR-0010](0010-activity-v0-service-ownership.md) и сохраняет
правила авторизации [ADR-0011](0011-activity-authorization-budget.md).
Существующий Core-модуль `leadstatus` из
[ADR-0009](0009-service-modules-and-fair-admission.md) не становится отдельно
размещаемым сервисом автоматически. Его перенос требует собственного scope.

## Владельцы и зависимости

| Владелец | Собственные данные и работа | Текущие разрешённые обращения |
| --- | --- | --- |
| Core API | Installations, integrations, browser admission, receipts и command outbox | Activity и CRM Events через порты; policy и OAuth bootstrap через Core worker/Gateway |
| Core worker/Gateway/policy | OAuth credentials, refresh, подпись delegation, исходящий бюджет amoCRM, существующие Core jobs | amoCRM и Core DB |
| CRM Events | Исходные события, coverage, source/consumer state, operations, inbox, очередь, leases, retention | Core policy; Gateway Events |
| Activity | Продуктовые настройки и receipts настроек; построение представления | CRM Events Query/Status/Operation; Core policy; ограниченный Gateway Users |

Activity не вызывает CRM Events Apply: команды коллектора идут через Core
outbox. Одна общая Go-интерфейсная декларация не расширяет разрешённые действия:
действуют точные grants, mTLS ACL и проверки владельца операции. В частности,
наличие `Events` в интерфейсе Gateway не разрешает Activity читать amoCRM напрямую.

Обогащение реализовано в [ADR-0014](0014-event-enrichment-contract.md): CRM Events
хранит полученные примечания/справочники и происхождение фактов в своей БД,
получая их через ограниченные Gateway-методы; Activity строит представление.
Произвольный HTTP-прокси и общий сервис справочников без второго потребителя
по-прежнему не вводятся.

## Контракт нового модуля

1. **Одна прикладная реализация.** Модуль принимает явные Repository/Policy/
   dependency-порты через конструктор. Embedded-адаптер и gRPC-сервер вызывают
   ту же реализацию. Проверки аргументов, policy, идемпотентности и результатов
   остаются в прикладном слое; транспорт не реализует их альтернативную версию.
2. **Собственный владелец данных.** Состояние модуля хранится в его логической
   БД с собственными миграциями и runtime-ролью. Модуль не получает чужой pool,
   DSN или Repository. Нет межвладельческих JOIN/FK/FDW/транзакций. Tenant IDs —
   внешние ссылки; допустимость операции проверяется через Core policy.
   Runtime-роль имеет только необходимые права своей БД, migration credentials
   доступны только мигратору. Физический PostgreSQL может пока оставаться общим.
3. **Секреты по владельцам.** OAuth credentials, ключи их шифрования и право
   подписывать delegation остаются у Core. Модуль получает собственные DSN и
   mTLS identity. Он не создаёт `amocrm.Client`, refresh-механизм или универсальный
   HTTP-прокси. Все новые amoCRM чтения расширяют ограниченный Gateway-порт и
   используют существующего единственного владельца исходящего бюджета.
4. **Явный wire-контракт.** Transport-neutral DTO и интерфейсы находятся в
   `internal/serviceapi`, protobuf и преобразования — в transport-слое. В
   продуктовых DTO нет SQL handles, ORM-моделей, OAuth credentials или generated
   RPC types. Существующий `CoreBootstrap.GetAccount` — отдельный Core-only
   контракт с временным токеном; продуктовым модулям он недоступен.
   Добавления v1 совместимы: номера protobuf-полей не переиспользуются,
   неизвестное необязательное поле не меняет смысл существующего метода.
5. **Авторизация при любом размещении.** Core определяет actor/installation/
   integration из проверенного browser context. Новый метод имеет audience,
   action и разрешённые вызывающие identities; policy недоступна — операция
   отклоняется как unavailable. Сохраняется модель ADR-0011: свежий Issue на
   новый запрос/доставку, короткий снимок роли и текущая Core DB policy на каждом
   переходе. Модуль не хранит browser JWT в durable работе.
6. **Долговечные команды по необходимости.** Для асинхронного изменения Core
   фиксирует admission и доставку, владелец атомарно дедуплицирует команду и
   создаёт свою operation/работу. Неоднозначный ответ повторяет тот же command
   ID, scope и payload. Очередь модуля не использует Core worker slots и чужую
   транзакцию. Read-only модулю очередь не нужна. Существующие outbox/inbox и
   паттерны leases/fencing расширяются в пределах их владельцев, а не заменяются
   новым общим event bus.
7. **Ограниченные ресурсы.** Для модуля определены pool, concurrency, deadlines,
   page/batch/response limits, retry и retention. Повышение числа реплик требует
   пересчёта суммарного бюджета и проверки leases. Метрики используют конечные
   labels; request/command ID передаётся для диагностики без токенов и payload
   с персональными данными в логах.
8. **Операционная самостоятельность.** Есть отдельный entrypoint, image target,
   конфигурация адресов, readiness/liveness, graceful shutdown и инструкции
   восстановления. Отказ удалённого dependency не включает скрытый embedded
   fallback. Перенос сохраняет БД владельца и командные идентификаторы; перенос
   самой БД — отдельная процедура с согласованным backup/restore.

## Статическая регистрация и границы реализации

[Catalog](../../internal/services/catalog.go) и
[Registry](../../internal/services/registry.go) статические. Добавление продукта
включает новую запись каталога, typed port/accessor и composition wiring в
[componentruntime](../../internal/componentruntime/runtime.go), а также transport
registration. Это допустимые изменения связующего кода; «без изменения
бизнес-логики» не означает «без регистрации нового продукта».

Текущие policy consumer/grants и список mTLS identities также статические:
`Consumer=activity` проверяется в
[policy.go](../../internal/corepolicy/policy.go). Новый продукт потребует явного
расширения capability, consumer admission и grants, а не выдачи себя за Activity.
CRM Events v0 поддерживает одного consumer; поддержку второго нельзя считать
готовой на основании наличия параметра в DTO. Нужны schema/policy/collector
сценарии независимого включения и отключения потребителей.

Для новых продуктов не вводятся dynamic plugin loader, универсальный
Service/Repository с произвольными строковыми методами или registry, исполняющий
продуктовый SQL. Модуль не импортирует реализации другого продукта, Core jobs,
OAuth, Gateway, transport и composition. SQL допускается в собственном
repository-адаптере; прикладной код зависит от Repository-порта. Сеть выполняется
в адаптерах, а не скрыто внутри прикладных функций.

[Boundary tests](../../internal/componentruntime/boundaries_test.go) автоматически
проверяют новые продуктовые каталоги `internal/services/*`; `leadstatus` исключён
как существующий Core-модуль. Тест с временным будущим модулем защищает сам
механизм проверки. Это статическая защита прямых импортов; косвенные/dynamic
сетевые вызовы через сторонний пакет она не доказывает и не исключает. Владение
runtime pool, policy и сохранность команд дополнительно проверяются
интеграционными и process-тестами. Для SQL-границы нового владельца
используется образец
[CRM Events boundary test](../../internal/services/crmevents/boundaries_test.go).

## Размещение: что работает сейчас и что ещё проверять

`ACTIVITY_MODE` в [config.go](../../internal/componentruntime/config.go) выбирает
`off`, `embedded` или `grpc` для графа Activity + CRM Events целиком. В `grpc`
адреса `ACTIVITY_ADDRESS`, `CRM_EVENTS_ADDRESS`, `GATEWAY_ADDRESS` независимы:
существующий отдельно запущенный процесс можно адресовать на другом хосте.
Смешанный вариант «Activity remote, CRM Events embedded внутри Core» сейчас не
реализован. Если он понадобится, менять нужно config/composition, сохраняя
прикладные реализации и wire-контракты.

При переносе между серверами необходимы маршрутизация, firewall, PostgreSQL TLS
и права подключения, стабильный DNS и сертификаты с соответствующими SAN.
Runtime использует hostname из адреса как TLS ServerName. Development generator
в [service-certs](../../cmd/service-certs/main.go) выпускает сертификаты только
для локальных имён сервиса/`localhost` и алиасов `api`/`worker`; произвольный
удалённый DNS или IP не покрывается ими автоматически. В production identities
выдаются выбранным CA с правильными DNS/IP SAN и SPIFFE URI; TLS verification
не отключается ради переезда.

Текущие process-тесты проверяют отдельные локальные процессы, изоляцию логических
БД и переключение embedded → gRPC → embedded. Они не доказывают сетевое размещение
на нескольких физических серверах, физическую изоляцию PostgreSQL или безопасное
горизонтальное масштабирование. Эти доказательства добавляются в этап приёмки
переноса и записываются отдельно от наличия кода.

## Совместимость и критерии приёмки расширения

- Одинаковые запросы в embedded/gRPC дают одинаковые полезные данные, коды
  ошибок, policy-отказы, границы ответа и состояния операций.
- Повтор command ID после restart, истечения lease или потерянного ответа
  не создаёт второй эффект. Upgrade сохраняет прежние durable payload, scope,
  hash, idempotency receipt, inbox, operation и queue state либо имеет явную
  совместимую миграцию. Очистка не укорачивает общий retry/dedup horizon.
- Совместимость предыдущего и нового клиента/сервера проверяется для выбранного
  порядка rollout. Если смешанные версии недопустимы, это явно фиксируется,
  старые executors останавливаются перед запуском новых. Разрушающий migration
  down не используется как обычный откат версии приложения.
- Отказ модуля, dependency timeout, исчерпание pool/слотов и policy revocation
  дают ограниченное и наблюдаемое поведение. Существующие Core ping и lead-status
  проходят регрессию; optional module outage не превращается в hidden fallback.
- Для заявления «перенесён на отдельный сервер» есть отдельный протокол с адресами
  размещения без секретов, версиями образов/миграций, проверками TLS/DB/повтора
  команды, результатом через прежний тестовый виджет и порядком возврата.

Пошаговый шаблон расширения и список точек wiring — в
[runbook нового модуля](../runbooks/new-product-module.md).
