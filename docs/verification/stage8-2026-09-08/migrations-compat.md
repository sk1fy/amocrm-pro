# Совместимость owner-миграций этапов 2–7

Дата: 2026-09-11. Схема по исходникам репозитория. На runtime/production эти
версии **не применялись в этой сессии**. Сверка этапа 1: живой локальный
кластер имел Core `000001–000011`, Activity `000001`, CRM Events `000001`
(без `000002`). Повторно к runtime-БД `amocrm_*` проекта `amocrm-activity`
не подключались.

Правило выпуска: сначала расширяющая миграция владельца, затем новый бинарь
этого владельца. Чужие БД не мигрировать «за компанию». Откат бинаря на
предыдущий — пока схема обратно совместима. `down` не возвращает удалённые
строки, ciphertext и tombstones. Пропуск `000013` в Core допустим.

Activity в этапах 2–7 owner-миграций не добавляла (`000001_settings` — база v0).

## CRM Events (`migrations/crmevents/`)

| Миграция | Этап | Совместимость старого бинаря после up | Новый бинарь до up | Rollback |
| --- | --- | --- | --- | --- |
| `000002_retention_consistency` | до этапа 2 (аудит v0); на runtime этапа 1 отсутствовала | Старый код с retention 1 или >30 получит ошибку CHECK. Данные не меняет, если все источники уже 2..30 | Новый код с узким диапазоном может писать значения, которые старый CHECK ещё принимает | down возвращает CHECK 1..90; `retention_checked_at` теряется. Строки не восстанавливает |
| `000003_event_details` | 2 EVT-02 | Старый код игнорирует `linked_talk_contact_id` (DEFAULT 0) | Новый код читает колонку — нужен up до старта | down `DROP COLUMN`; значения колонки теряются |
| `000004_event_enrichment` | 3 ENR-02 | Старый коллектор таблицы не трогает | Enrichment-бинарь без таблиц не стартует работу ENR | down удаляет objects/links вместе с фактами |
| `000005_enrichment_refresh` | 3 (ревью) | Индекс шире; старый claim-SQL продолжает работать | Новый TTL/claim ожидает индекс и сброс `event_payload` | down не возвращает сброшенные payload |
| `000006_enrichment_retry_recovery` | 3 (аудит) | Data-only UPDATE `error/temporary` → `retry` | Новый recovery ожидает, что старые terminal temporary снова в очереди | down нет обратного UPDATE; состояние retry не откатить этим файлом |
| `000007_technical_history` | 6 REL-03 | Старый код не читает `event_sources.events_*` | Новый `SavePage`/метрики требуют колонок | down дропает колонки-счётчики; накопленные totals теряются |
| `000008_command_identity_horizon` | 7 CORE-05 | Старый Apply пишет inbox; trigger отклонит tombstoned ID (для старого кода это ошибка unique) | Новый GC/Apply ждут таблицу tombstones | down удаляет tombstones и trigger; защита от late replay пропадает, данные inbox не возвращаются |

Порядок Events: `000001` → `000002` → … → `000008`. Не применять `000008` без
`000007`. Не применять `000005`/`000006` без `000004`.

## Core (`migrations/`)

| Миграция | Этап | Совместимость старого бинаря после up | Новый бинарь до up | Rollback |
| --- | --- | --- | --- | --- |
| `000012_oauth_refresh_lease` | 7 CORE-01 | Старый refresh не использует lease-колонки; NULL допустим | Новый claim/lease пишет `lease_token`/`lease_until` | down дропает колонки; незавершённый claim теряется, токены не «откручиваются» |
| `000014_core_redelivery_horizon` | 7 CORE-05 | Старый worker не ставит `expired`; CHECK после up допускает extra status | Новый worker/GC пишут `expired` — без up INSERT упадёт | down мапит `expired`→`failed` и сужает CHECK. Удалённые GC-строки не возвращает |
| `000015_webhook_ownership` | 7 CORE-02 | Старый код таблицу не читает | Uninstall/owned destinations требуют таблицу | down дропает destinations; ciphertext URL теряется, подписки в amoCRM сами не восстанавливаются |

База Core `000001–000011` считается уже на runtime этапа 1. Их повторно не
накатывать. `000011_activity_delivery` обязательна до продуктовых команд.

## Порядок выкладки по владельцам

1. CRM Events migrate up до нужной версии, затем бинарь `crm-events`.
2. Core migrate up (`000012`, `000014`, `000015` по мере выпуска), затем
   api/worker. Keyring тот же.
3. Activity бинарь; owner-схема этапа 2–7 не менялась.
4. Не стартовать новый Events до `000007`, если бинарь уже читает `events_*`.
5. Не стартовать новый Core до `000012`, если бинарь пишет OAuth lease.

Откат выпуска: предыдущие образы + dump, снятый **до** миграции. После up
обратный бинарь допустим только пока он не пишет статусы/колонки, которых
нет в down-схеме. Для `000014` старый бинарь после up безопасно не ставит
`expired`. Для `000007` старый Events после up безопасен; новый Events после
down — нет.
