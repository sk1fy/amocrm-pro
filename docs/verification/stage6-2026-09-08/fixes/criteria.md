## L-03: реальный транспорт

`TestStage6TransportMeasure`: PostgreSQL → CRM Events gRPC/mTLS → Activity
gRPC/mTLS → штатный HTTP handler и loopback HTTP-клиент. Policy/справочник —
синтетические порты; это не проверка production auth и не раздельные OS-процессы.

100 событий с `value_before` и `value_after` по ~32 KiB. Двоичный поиск последней
допустимой non-compact страницы по реальному HTTP; body должен заполнить ≥90%
от 3 MiB. Следующий limit и limit=100 должны вернуть HTTP 429 /
`resource_exhausted`, compact=100 и одна карточка — полный успешный ответ.
Размеры protobuf измеряются по реальным ответам generated клиентов, без копий
production conversion. Успешный HTTP body ≤3 MiB, protobuf <4 MiB.

Полный opt-in: 3 прогрева и 25 samples на каждый сценарий. Время HTTP измеряется
до полного чтения body. Сохраняются прежние пороги: Panel P95≤1.2s / P99≤2.5s;
EventCard P95≤300ms / P99≤700ms. Обычный gate выполняет функциональную проверку
этих же границ с одним sample, без заявления о P95/P99.

## L-01: работа workers

`TestStage6WorkersUnderSharedBudget`: пять установок, штатный `Service.Run`
(scheduler, два worker, RunOnce/EnrichOnce), общий fixture-бюджет 20 внешних
запросов/секунду с burst=1 и задержкой ответа 20ms. Профиль — 6 волн по одному
новому task-событию на установку с интервалом секунду, 200 backfill-событий на
установку и по одному ready-объекту с истёкшим refresh. Обычный gate использует
2 волны и 20 backfill-событий на установку; все пять установок сохраняются.

До прогона фиксируются критерии: все новые события и детали получены для каждой
установки; все пять backfills завершены; due enrichment-очередь опустела за 30s.
Задержка от поступления события до ready-детали: P95≤15s, P99≤20s. Максимальный
collector lag≤15s. Обязательны ненулевые фактические Events/Tasks/refresh calls
и refresh всех пяти seed-объектов. Доля refresh измеряется по выполненным Tasks
запросам, включая запросы со смешанным batch. Возраст jobs/enrichment, collector
lag, число готовых деталей записываются серией во времени; отдельно — ожидание
общего бюджета и время до появления исходного события.

Первый полный прогон выявил превышение batch limit в SQL claim (200 вместо 50).
Добавлена отдельная регрессия и усилена проверка: все объекты backfill также
должны стать ready, а не исчезнуть из due-очереди с `unavailable/invalid`.
Исходные объёмы и пороги задержек сохранены.

Пороги не увеличиваются при FAIL. Full-profile запускается отдельно от тяжёлого
общего gate. Артефакты записываются в `fixes/rel-02/`, исходные измерения сохранены.

## Очистка

Регрессии из ревью обязаны проходить как без GC, так и с GC. Старый command ID
сохраняет операцию и hash Conflict после удаления завершённых jobs; старый sync
не откатывает более новые настройки. Paused backfill после reauth возобновляется
в исходном диапазоне. Inbox и operations пока не чистятся: максимальный срок
redelivery Core, включая простой и операторский retry, остаётся CORE-05.
