# CRM Events: исправления аудита 7 сентября 2026

## Изменено

- Retention обрабатывает один источник за вызов, не более `RetentionBatch`
  событий. Источники посещаются по `retention_checked_at`, поэтому большой
  источник не забирает каждый проход. Занятый source пропускается через
  `FOR UPDATE SKIP LOCKED`; поиск старых событий использует существующий индекс
  `(installation_id, created_at, event_id)`.
- Удаление и продвижение `retained_from` коммитятся в одной транзакции под тем
  же source lock, который защищает запись страницы. При частичном batch
  граница продвигается только за максимальную удалённую метку времени, округляя
  её вверх до следующей секунды. Это консервативная граница гарантированной
  сохранности истории, а не утверждение, что все более старые записи физически
  удалены. При неполном/пустом batch достигается retention cutoff. Граница
  монотонна даже при увеличении retention; пустое окно не превращается в
  «проверенное» по наличию или отсутствию событий.
- Query читает status, страницу и агрегаты в одной read-only repeatable-read
  транзакции. Поэтому конкурентная очистка не смешивает прежнюю границу
  сохранности с уже очищенными данными. Status также использует один snapshot.
- SavePage читает все прежние хеши страницы одним запросом и пишет конечные
  версии событий через `pgx.Batch`, сохраняя порядок блокировок. Повтор одного
  ID внутри страницы обрабатывается последовательно при подсчёте
  inserted/updated/deduplicated, затем записывается один раз. Взамен двух
  сетевых round-trip на событие используется один hash SELECT и один batch
  exchange. Это сокращение round-trip, а не заявление об измеренном ускорении
  SQL или об устранении всех отдельных серверных INSERT.
- Добавлен индекс `event_operation_jobs(job_id)`.
- После допуска и получения страницы запись успеха либо ошибки получает
  отдельный `WithoutCancel` context с дедлайном: по умолчанию 5 секунд,
  конфигурационный максимум 5 секунд. Fencing token и проверка lease/disable
  остаются обязательными; graceful shutdown не даёт права обойти их.
- Ошибки collect/fetch/validate/schedule/retention больше не теряются: logger
  выдаёт только stage и конечный набор error codes, без upstream payload,
  SQL, токенов и произвольных текстов ошибок. Один stage/code логируется не
  чаще раза в минуту на экземпляр Service. Необязательный `Config.Logger`
  по умолчанию — `slog.Default()`.
- Граница retention в приложении и БД согласована с Activity: 2–30 дней и
  прикладная проверка `retention >= initial_days`.

## Миграция

Добавлена `migrations/crmevents/000002_retention_consistency.up.sql` и down.
Миграцию выполняет владелец CRM Events БД. Если в старой БД есть значения
retention вне 2–30, миграция явно завершается ошибкой **до изменений**, не
сокращая 90 дней до 30 автоматически. Перед обновлением оператор проверяет:

```sql
SELECT installation_id, retention_days
FROM event_sources
WHERE retention_days NOT BETWEEN 2 AND 30;
```

При наличии строк оператор должен отдельно согласовать новую политику
хранения, обновить её владельцем БД и повторить миграцию. Снижение retention
разрешает последующей очистке удалить старые события; это не техническая
операция, которую следует выполнять молча. Down возвращает прежний CHECK и
удаляет новые индексы/служебную колонку, не возвращая уже удалённые события.

## Фактически проверено

Docker `golang:1.25`, PostgreSQL 17 из локального изолированного dev-стека,
отдельная тестовая БД `crm_events_audit_test`; runtime БД не менялась:

```sh
docker run --rm --network amocrm-activity_default \
  -v "$PWD:/src" -v amocrm-pro-gomod:/go/pkg/mod \
  -v amocrm-pro-gobuild:/root/.cache/go-build -w /src \
  -e CRM_EVENTS_TEST_DATABASE_URL='postgres://pilot_admin:pilot_admin_dev@postgres:5432/crm_events_audit_test?sslmode=disable' \
  golang:1.25 sh -ec 'go vet ./internal/services/crmevents; go test -race ./internal/services/crmevents -count=1 -v'
```

Выполнено успешно: `go vet` и 30 верхнеуровневых тестов под `-race`,
без пропусков; полный лог локального прогона — `/tmp/events-audit-tests.log`.

Регрессии проверяют:

- больше одного batch, чередование источников, пропуск занятого источника;
- rollback удаления при ошибке обновления frontier;
- пустые и ещё не проверенные источники, монотонность при расширении retention;
- настоящий Query, приостановленный после чтения status, конкурентный Retain
  и согласованную старую страницу/агрегаты, затем новый snapshot;
- вставку/изменение/дедуп одного ID внутри одной страницы;
- отказ миграции для legacy 90 без изменения значения и успешный down/up для 30;
- успешную страницу, некорректную страницу и network error при отмене fetch context;
- ограничение повторных логов и отсутствие произвольных секретных строк;
- некорректную upstream страницу без записи/coverage и новую sync, которая
  повторяет тот же fixed window/page и завершается после исправления upstream.

## Сохранённые ограничения

- По-прежнему один общий лимит batch за минуту на процесс: один источник
  посещается за тик, при N свободных источниках полный обход занимает примерно
  N минут. Это ограниченная очистка с равными очередями, не обещание мгновенного
  физического удаления или проверенной производительности большого парка.
- Некорректное окно не пропускается, timestamp не исправляется догадкой.
  Если upstream постоянно возвращает ошибку, новая sync снова остановится.
- Глобальная короткая advisory-блокировка допуска backfill сохранена:
  исправление не ослабляет общий лимит backfill между worker replicas.
- Техническая история inbox/jobs/operations не очищается: безопасный GC требует
  отдельного срока дедупликации и публичной семантики позднего повтора команд.
- Backfill продолжает применять доставленный снимок настроек к источнику;
  изменение этой семантики не входило в исправление подтверждённых дефектов.
- Новый код не развёрнут на сервере и не проверен заново в живом amoCRM.
