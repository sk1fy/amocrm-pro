## CORE-06: аудит выполнен, требование least privilege не выполнено

Подтверждено:
- Activity/Events runtime — NOSUPERUSER/NOCREATEDB/NOCREATEROLE;
  DML таблиц, USAGE схемы, без CREATE/TRUNCATE. DDL остаётся у owners.
- Между Activity и Events запрещён чужой CONNECT.
- Management API 8082 опубликован только на 127.0.0.1; 8091/8092 не
  публикуются. Nginx проксирует публичные запросы на 8080;
  внешние /components, /ready, /metrics отвечают 404.

Найдено:
- Core API/worker используют роль amocrm с SUPERUSER, CREATEDB,
  CREATEROLE, BYPASSRLS. Она владеет Core-БД amocrm.
- Core-БД сохраняет PUBLIC CONNECT+TEMP: чужие Activity/Events-роли
  могут подключаться к ней, хотя SELECT Core-таблиц им не разрешён.
- Схема public имеет PUBLIC USAGE, без PUBLIC CREATE.
- UFW inactive, INPUT ACCEPT; внешняя экспозиция ограничена bindings
  и nginx, доступны 22/80/443. Это наблюдение, не доказательство
  публичной доступности management.

Оставлено открытым: согласованная миграция Core на отдельные owner/runtime
роли для фактической БД amocrm, отзыв лишнего PUBLIC CONNECT/TEMP,
проверка всех зависимостей и восстановления, затем отрицательные тесты прав.
Нельзя просто применить development init-db.sh к существующему кластеру:
он рассчитан на fresh cluster и имя amocrm_core.
ACL, firewall, credentials и KMS в этом проходе не менялись.
