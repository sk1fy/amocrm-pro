# ColorLeads: подготовка снимка и сверка

Инструмент работает только с локальными файлами. Он не читает production БД,
не вызывает amoCRM, не импортирует данные и не разрешает переключение владельца.
Это подготовительная часть ПВ-04.04; серверная команда находится в
`internal/colorleads.ImportSnapshot`. Её подключение требует готового ПВ-03.

Входной экспорт одного аккаунта:

```json
{
  "schema_version": 1,
  "product_code": "rkrs_color_leads",
  "account_id": 42,
  "source": {
    "platform": "ssd",
    "revision": "verified-export-version",
    "boundary": "verified-final-boundary-reference",
    "exported_at": "2026-10-22T00:00:00Z"
  },
  "settings": {"main_settings": []},
  "colors": []
}
```

Это пример, а не подтверждённый аккаунт/receipt. Оператор экспорта должен
получить согласованный снимок после остановки source writer. Строки `source`
сохраняют происхождение; скрипт не проверяет подлинность остановки. Серверный
ImportGuard обязан независимо проверить transfer, авторизацию, scope, epoch,
generation и остановку всех прежних исполнителей в транзакции.

`settings` — эффективные настройки: если WidgetSetting отсутствует, сначала
нужно явно разрешить fallback `Widgets.widget_init_setting` как в SSD.
Пустой массив/false нельзя молча заменить объектом: оператор должен установить,
что это отсутствие правил, и сохранить исходные значения в архиве экспорта.
Неизвестные ключи объекта сохраняются; порядок правил значим.

В `colors` передаются исходные строки с `lead_id`, `stage_id`, `pipeline_id`,
`borderColor`, `backgroundColor`, `timestamp`; optional `amo_account_id`
должен совпадать со scope. Неизвестные поля и исходные ID остаются в
`source_rows` кандидата как архив, а не продуктовые поля Core. Отсутствующий
цвет/время нормализуются в null. Числовые timestamps, невалидные ID и дубликаты
составного ключа отклоняются для явного разбора — скрипт их не угадывает и
не схлопывает. Полноту выгрузки проверяет экспортёр по фактической БД.

```sh
python3 scripts/color-leads/snapshot.py plan source.json > candidate.json
python3 scripts/color-leads/snapshot.py reconcile source.json core-export.json
python3 -m unittest discover -s scripts/color-leads -v
```

Коды завершения: 0 — кандидат совместим / данные совпали; 1 — расхождения
или ограничения текущего Core (список `blockers`, без усечения данных);
2 — недопустимый ввод. Сверка сравнивает ключи и значения, а не только число
строк. Она не доказывает права, оплату, остановку старой вкладки или UI parity.
Для Core snapshot передаётся только `{settings, colors}` из `payload`.
Installation, transfer, actor, epoch и generation задаёт доверенный серверный
command adapter. `source_sha256` связывает ImportCommand.SourceDigest с полным
архивом экспорта, который должен храниться отдельно с ограниченным доступом.
`payload_sha256` — digest локального формата; это не digest
Go-команды и не подпись receipt. Не подставлять его вместо серверного digest.

Возврат сверяет новый экспорт актуального Core с результатом обратного импорта
в SSD. Исходный архив SSD не используется поверх изменившихся данных.
Автоматического обратного импортёра пока нет: требуется согласовать SQL-схему,
семантику дублей и вернуть новые settings/colors после остановки Core.
Второй перенос в существующий документ Core намеренно отвергается до реализации
явной политики сверенного повторного импорта. Это блокирует живую приёмку
ПВ-04.06, а не разрешает потерять изменения ради возврата.
